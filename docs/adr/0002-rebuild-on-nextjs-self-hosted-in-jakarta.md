# Rebuild v1 from scratch on Next.js, self-hosted on the shared Jakarta VPS

v1 is a fresh TypeScript codebase (Next.js App Router, Postgres + Drizzle, pg-boss, Better Auth), not a continuation of the existing Laravel app at `/home/ubuntu/makam-app` (Laravel 13 / Livewire / Filament, ~1,500 commits, dev and beta running), which is frozen as reference. We chose TypeScript because the builder is one engineer working with AI agents and wants the stack those agents write most reliably, with one language across UI, back office and domain logic; the accepted cost is losing Filament's generated admin panels and rebuilding the back office by hand. Production runs on the same Jakarta VPS that hosts makam-app's nonprod and other projects, with a self-managed Postgres, rather than a managed database: it keeps primary data in Indonesia (no UU PDP cross-border transfer) at almost no cost. The accepted risk is one shared machine, mitigated by a separate `makam-prod` compose project with its own Postgres, daily off-host backups to Indonesian object storage with restore tests, and an external uptime alarm. Managed Postgres options with a Jakarta region (GCP Cloud SQL, AWS RDS) remain the move if that risk stops being acceptable.

This corrects the last sentence of the amendment above ("`dev.makam.co.id` is unaffected").

- **`dev.makam.co.id` now serves v1 staging** (compose project `makam-staging`) behind HTTP basic auth, replacing the frozen Laravel app's dev environment there, as the user approved on 2026-09-25. - **Deploys are pull-based, not pushed by CI.** CI builds and pushes `ghcr.io/andrianm28/makam` (`latest` and `sha-<commit>`, from `main` only, after the checks pass) and never connects to the VPS. On the host, a systemd timer runs `makam-deploy`, which pulls the image with a read-only `read:packages` token, runs `migrate`, and runs `up` only if the migration succeeded. We chose this over CI deploying over SSH because it keeps no deploy key or host secret in GitHub and needs no inbound access to the shared machine. Accepted cost: a deploy lands up to about 2 minutes after the image is pushed, and a failed deploy shows up in the host's journal and `deploy.log` rather than in the CI run. Production (ticket 65) deploys an explicit tag with the same script instead of following the timer.

## Amendment (2026-09-25, later): email goes through SumoPod SMTP, SES dropped

- **The app sends every email through the SumoPod SMTP relay** (`smtp.sumopod.com`, port 465, SMTPS), directly from its `EmailSender` adapter: login codes, the email fallback after a WhatsApp code, copies of Tagihan and Bukti, and staff invites. **Amazon SES is dropped from v1.** Why: the frozen Laravel app already sends `no-reply@makam.co.id` through this relay in production, SumoPod is already the Operator's payment vendor, and it removes SES's domain set-up and sandbox exit from the launch path. AWS is now used for S3 only (files and backups). Accepted cost: email deliverability depends on one more SumoPod service and on the domain authentication (DKIM, SPF, DMARC) being published for `makam.co.id`, which today has none.
- **The self-hosted Stalwart mail server on this host is for human mailboxes only.** The app never sends through it. It is not a fallback relay, because its IP has no sending reputation or rDNS.
- Email is a flow of personal data (addresses, codes, document copies) to SumoPod; where SumoPod's relay processes it has not been confirmed yet (ticket 04).

## Amendment (2026-09-26): deploys run from GitHub Actions through a self-hosted runner

This replaces "Deploys are pull-based, not pushed by CI" (second amendment of 2026-09-25) and the matching line in the spec. User decision.

- **GitHub Actions is the whole pipeline, including deploys.** PRs run lint, typecheck, Vitest and an image build without push. `main` also pushes `sha-<commit>`, runs the Playwright critical paths against that image on a GitHub-hosted runner and scans it (Trivy, fail on critical). Staging then deploys that image automatically; production **promotes the exact digest already green on staging** (no rebuild) through the GitHub Environment `production`, which requires the user's approval, and tags the release `vYYYY.MM.DD-N` with generated notes.
- **Deploy jobs run on a self-hosted GitHub Actions runner on this host**, as an unprivileged user, used for deploy jobs only (never build or test, to spare the shared machine's disk). The runner only opens outbound connections to GitHub: there is still no inbound SSH, no deploy key and no host secret in GitHub. The job calls the same `makam-deploy` script, so the deploy result now shows in the GitHub run and as a GitHub Deployment. We chose this over staying pull-based (deploys invisible in GitHub) and over SSH from a hosted runner (a deploy key in GitHub and SSH open to GitHub's changing IPs). Accepted cost: anyone who can push a workflow to the repo can run code on the host as the runner user, so workflow changes stay reviewed and the runner user has no sudo and only the docker access the deploy needs.
- **Environment secrets stay on the host** (`/opt/makam-v1/<env>/<env>.env`); GitHub holds only its own ghcr token. Because one digest serves both environments, nothing environment-specific may be baked into the image at build time (the browser GlitchTip DSN becomes a runtime value).
- **Production safety**: a `pg_dump` snapshot before every production `migrate` (local now, also off-host once ticket 64 exists); migrations are expand/contract so the previous image keeps working on the new schema; a failed healthcheck rolls back to the previous image automatically; migrations are never rolled back automatically. Production does not go live before ticket 64's off-host backups.
- **The `makam.co.id` switch from the old app stays a one-time, human-gated step** (ticket 65), outside the pipeline.
- **Disk on the shared host**: each deploy keeps only the last 3 makam image versions per environment, and a monthly workflow deletes ghcr `sha-*` tags older than 30 days that are not deployed.

## Amendment (2026-09-26, later): pull-based deploys stay, hardened with signed images

This **replaces the previous amendment** ("deploys run from GitHub Actions through a self-hosted runner"), which the user approved before a constraint surfaced: the repository is private on the **GitHub Free** plan, which offers no branch protection or rulesets, no environment required reviewers, no deployment-branch restrictions, and no artifact attestations, secret scanning or code scanning. Without branch restrictions, a workflow on any branch could run on a self-hosted runner on the shared host, and the planned approval gate did not exist. User decision.

- **Deploys stay pull-based** (the host pulls; CI never runs code on the host, no runner, no inbound access). The host reports each deploy to GitHub as a Deployment status with a fine-grained token limited to deployment statuses on this repository, so every deploy is still visible in GitHub.
- **Only signed images are deployed.** CI signs every image that passed the checks, e2e and the scan with a cosign key pair (private key as a GitHub secret, public key on the host); `makam-deploy` verifies the signature before `migrate` and refuses unsigned images. A leaked ghcr token therefore cannot get an image deployed.
- **Production promotion** is a manual `workflow_dispatch` ("Promosikan ke produksi") that refuses unless run by the repository owner, requires the release tag to be typed again, requires the digest to be the one deployed and healthy on staging, and signs it with a **separate production key**; the production host accepts only production-signed images. It tags `vYYYY.MM.DD-N` with generated notes. A matching manual rollback workflow re-promotes an earlier digest.
- **No GitHub Pro for now.** Merges to `main` are made only by the orchestrator after the two-axis review and the user's approval; deploys are gated by job `needs:` on checks, e2e and scan.
- **Supply chain**: actions pinned by full commit SHA, container images by digest, Dependabot for actions, npm and Docker, gitleaks for leaked secrets, `npm audit` and Trivy (fail on fixable CRITICAL), an SBOM per image, least-privilege `permissions` and `timeout-minutes` on every job. No CodeQL (needs GHAS).
- **Migrations**: a CI upgrade test migrates a database holding the running release's schema and data; destructive DDL fails CI unless marked `-- contract:` with a reason, enforcing expand/contract. A `pg_dump` snapshot precedes every production `migrate`; a failed healthcheck rolls the image back automatically; migrations are never rolled back automatically.
- **After deploy**: a Playwright smoke test against `https://dev.makam.co.id` from a hosted runner must pass before promotion; source maps are uploaded to GlitchTip on each build (release-scoped token as a GitHub secret); each deploy creates a GlitchTip release.
- **Concurrency**: builds may cancel superseded builds; deploy, promotion and rollback run in their own groups and are never cancelled mid-way.
- Unchanged from the previous amendment: secrets stay on the host, one digest serves both environments (nothing environment-specific baked in), image retention on the host, production not live before ticket 64, the `makam.co.id` switch stays in ticket 65.
