# 01: Probe: how skills load and expand in cloud threads

Spec: `.scratch/agent-orchestration-skills/spec.md`.

**What to build:** A short, recorded probe, run as real cloud-session threads started by the coordinator with a throwaway test skill on a scratch branch of makam, that answers the questions the brief format and coordinator rotation depend on. Its answers decide how every later ticket briefs a thread. Ticket 87's builder already answered part of the fourth question (makam-v1-build ticket 87's Comments): cite it and fill the gaps.

**Blocked by:** None (can start immediately).

**Status:** resolved

- [ ] Whether a prompt that starts with `/<skill> <arguments>` expands into that skill when it is a `create_session` prompt, and when it is a Routine prompt delivered into an existing session; whether a plain sentence naming the skill makes the thread invoke it.
- [ ] Whether checking out a branch that predates the skill removes it mid-session (the loaded body versus its references and hooks), and what a thread must therefore read before any checkout.
- [ ] Whether a sub-agent defined in the repository can preload skills (`skills:`) and use the Skill tool inside a cloud session, so a builder sub-agent follows `tdd` and `diagnosing-bugs` without being told which file to read.
- [ ] What a cloud session exposes about itself (session id, outcome branch, current branch) that a hook or a report-back can rely on.
- [ ] What happens to a one-shot Routine bound to a session that has since been archived (it fails, it revives the session, or it is dropped), for coordinator rotation; and whether one cloud session can message another with `claude -p … --cloud <session>`.
- [ ] Every answer recorded under `## Comments` with its evidence (session ids, outputs); the throwaway skill and branch removed afterwards (the owner deletes the branch).

  2. **Checkout without the skill.** C verbatim after `git checkout --detach origin/main` (3467f785): `.claude/skills/probe-marker` does not exist; the Skill tool answers `<tool_use_error>Unknown skill: probe-marker</tool_use_error>`; its `references/` are gone with the directory, so the body already loaded is the only thing left (the skill list is re-read from disk on each call). Rule for briefs: a thread reads every skill file it needs (body and references) before any checkout, or checks out a branch that carries them. Settings hooks live in `.claude/settings.json` and are likewise branch-bound (ticket 87: "Threads on a branch cut before this merge have no hooks").
  3. **Sub-agent preload.** B (summary): `probe-agent` was dispatched, "ran skill via preload, not Skill tool; no errors", reported the skill marker (`args=gamma`) and the reference output: **preload via `skills:` works**; the agent did not need the Skill tool. C: the same Agent call (`subagent_type: probe-agent`, `model: sonnet`) was **denied by the auto-mode classifier** (`[Auto-Mode Bypass]`, verbatim in C.md section 3), twice-identical dispatch not retried. So preload works when the dispatch is allowed, but in auto permission mode a dispatch can be refused for a repository-defined agent; whether the agent's own `Skill` tool call works is **not established** (B's agent did not call it). A builder brief must therefore not depend on the agent calling Skill itself; rely on `skills:` preload and still name the file as fallback.
  4. **What a session exposes** (ticket 87's builder: `CLAUDE_CODE_REMOTE_SESSION_ID=cse_<id>` = `session_<id>`; `CCR_SESSION_PROFILE` held the outcome branch in one session, empty in another). Added here: `CCR_SESSION_PROFILE` is **empty** in this coordinator session (outcome branch `aos-01-probe`) and in C although C was created with `outcome_branch: aos-01-probe-report-c` (C.md section 1), so it is not a role or branch source. `CLAUDE_CODE_BASE_REF` = the `source_revision` the session was created from (`coordinator-docs-aos-tickets` here, `aos-01-probe` in C), not the outcome branch. `CLAUDE_CODE_SESSION_ID` is a separate local uuid. Also set: `CLAUDE_CODE_REMOTE=true`, `CLAUDE_CODE_CHILD_SESSION=1`. **Outside the session**, `get_session`/`list_sessions` give `session_context.outcomes[].git_repository.git_info.branches` (the outcome branch), `external_metadata.current_branches` (current branch, e.g. `{"":"aos-01-probe-report-a"}` after A switched), `status_bucket` and `post_turn_summary` (the only readable result of a turn without a pushed file). Inside a session the outcome branch is reliably known only if the brief states it; the current branch is `git branch --show-current`.
  5. **Archived session and Routine.** `create_trigger` bound to an archived session is **refused at creation**: "Session ... is archived; only active sessions can be bound to triggers". A Routine created while the session was active and then archived (session unarchived, trigger `trig_01CWP2nnAVSh1C6Bwid8GvoT` created for 13:36:14Z, session archived again): at fire time (13:36:56Z) the run was `ROUTINE_RUN_STATUS_FAILED`, the trigger became `enabled=false`, `ended_reason=auto_disabled_session_gone`, `persistent_session_id` cleared, and the session **stayed archived** (not revived, no turn). So an archived thread's pending Routines are dropped with a failed run and the coordinator must re-create them on the successor. `unarchive_session` revives a session on demand (status PENDING, fresh container; `current_branches` and summary kept). Routine delivery lag: 40-80 s after `run_once_at`. **`claude -p "ping" --cloud session_01Fm4zLBHoV5MTxPbXkfmnyb`** from a cloud session: `Error: failed to send message to cloud session ...: Session expired. Please run /login to sign in again.` (CLI 2.1.288, exit 0 printed by the pipe): no sign-in in a cloud container, so **no**; `SendMessage` and `ListAgents` also see no other session ("No reachable agents"); the only cross-session channels here are `create_session` (user turn) and Routines (synthetic turn).
