# Agent orchestration skills: a Claude Code Projects alternative on Matt Pocock's workflow

Status: spec, owner decisions of 2026-10-03 (option tool). Tickets come from the owner's `/to-tickets` on this file.
Design input: `docs/agents/orchestration-optimization.md` (771e355); decisions recorded in ticket 87's `## Comments` (makam-v1-build).

## Goal

Generic, reusable skills that let one coordinator session in Claude Code on the web run multi-agent development through cloud-session threads, **as an alternative to Claude Code Projects**, while **orchestrating Matt Pocock's skills workflow and never replacing or bypassing it**. Makam is the first project to use them; any repository can adopt them with one sync command and one profile file.

## Owner decisions this spec carries (2026-10-03)

- **Home and distribution**: a separate repository `andrianm28/agent-orchestration-skills` (the owner creates it and gives Claude access). Projects vendor a pinned version into `.claude/skills/` with a sync script, because cloud sessions load repository skills and not `enabledPlugins`.
- **Shape**: two generic skills, `agent-coordinator` and `agent-thread` (with one reference per role), plus one profile file per project that holds everything project-specific.
- **Matt's skills travel with them**: the sync script also vendors an explicit list of Matt Pocock's skills (including `codebase-design` and `setup-matt-pocock-skills`) pinned at upstream's 1.2.3 release, with their LICENSE (owner, Q1: before the unreleased v1.3 changesets that retire `resolving-merge-conflicts` and rename `CONTEXT.md` to `GLOSSARY.md`; a sync never changes `CONTEXT.md` handling). `resolving-merge-conflicts` stays as a project-local copy with credit; a project drops any unpinned upstream plugin from `.claude/settings.json`; the owner runs `/setup-matt-pocock-skills` once per project.
- **Conformance with Matt's workflow** (no exceptions): decisions through `grilling`, one round holding the whole frontier with a recommended answer each (Q5), and `domain-modeling` only when a term or an ADR is at stake (`CONTEXT.md`; an ADR only when hard to reverse, surprising and a real trade-off); a full design interview is the owner's `/grill-with-docs`; investigations through `research`; UI uncertainty through `prototype`; builds and fixes test-first through `tdd`, a bug ticket or an unexplained red starts with `diagnosing-bugs` (D8 accepts its first loop through `TDD-exempt:`); every branch reviewed by `code-review` on both axes as two parallel sub-agents (D2, single-agent reviews, was revoked), and every re-review is a fresh two-axis `code-review` whose Spec axis also checks the earlier findings item by item (Q3); merges resolve conflicts with `resolving-merge-conflicts`. The owner-only skills (`to-tickets`, `handoff`, `grill-with-docs`) are never invoked by an agent: the coordinator prepares the material and asks the owner to run them. New work becomes tickets only through the owner's `/to-tickets`; an agent that stops early writes a progress note (`AGENTS.md` calls it HANDOFF; renamed in B so it does not read as the owner's `handoff`).
- **Process decisions from the analysis**: D1 CI on `merge/**` is the gate before `main`, the next merge starting at the push (local gate as fallback); D3 the coordinator stays on Opus and, at about 200k tokens and a point with no thread running, restarts from durable state (Q4): it starts its successor itself from the registry, the memory file, the tickets' Comments and `list_triggers`, with no conversation summary (`/handoff` stays the owner's, for when the owner wants one), re-points the open report-backs and sends the owner the new session's link; D4 idle mode (with nothing running, no hourly Routine, no watcher, no status); D5 enforcement in settings (being built in makam as ticket 87 Added, branch `ticket-87-penegakan`); D6 a GitHub ruleset on `main` (owner); D7 a merge thread batches up to three clean branches, at most one migration, money code alone; D8 a blocking `test(red)`-before-code check with a `TDD-exempt:` trailer, run when a thread reports done and in the merge thread, not per commit (Q9).
- **Ticket threads** (owner, 2026-10-03: trial now on this set's ticket 04 with a hand-written brief, its outcome feeding ticket 06 (Q10); then the default): one cloud thread per ticket runs, in its own VM, the build (a builder sub-agent with `tdd` and `diagnosing-bugs` preloaded through `skills:` and the Skill tool in its `tools`, as 01's probe confirms in cloud; reading each `SKILL.md` and its references by path is the fallback), the review (`code-review` run by the ticket thread itself: two parallel sub-agents, Opus for money code), the fix pass (a fresh builder sub-agent that checks out the ticket branch, never `origin/main`, and starts from a red test reproducing the finding) and the re-review (a fresh two-axis `code-review`, Q3), writes each report into the ticket before acting on it, keeps its own context small (a progress note at about 100 tool calls or 250k tokens, Q8), and reports back once: ready to merge, or a decision needed. The merge thread stays separate.
- **Operations**: up to five threads at once (owner); one number per limit (Q8): threads about 100 tool calls or 250k tokens, the coordinator about 200k; decisions in whole-frontier rounds (Q5): the round in text, a notification, then the option tool only to collect the answers (at most four per call); reconciliation on every wake (Q2); finished threads archived; the coordinator asks the owner to delete merged branches.

## The Projects mapping the skills must provide

| Claude Code Projects | Provided by |
|---|---|
| Coordinator conversation | a coordinator cloud session running `agent-coordinator`, restarted from durable state at about 200k (D3, Q4) |
| Threads | `create_session` with a role brief that runs `agent-thread`; one ticket thread per ticket by default (build, review, fix pass, re-review inside), plus the merge thread |
| Native report-back | a one-shot Routine bound to the coordinator's session (in the `create_trigger` tool contract, not in the public routines docs), plus reconciliation on every wake: `get_session` on every working thread, its branch head and the Routines that fired (Q2) |
| Reply into a running thread | a one-shot Routine bound to that thread's session |
| Overview | an owner-visible Artifact status page backed by its database, with a "Waiting on you" column from `status_bucket` blocked or failed (Q6); it holds the registry, so the registry survives a rotation |
| Project instructions | the project profile plus a short per-role `append_system_prompt` |
| Project memory | a memory file of at most about 40 lines (an index) `@`-imported from `CLAUDE.md`, so every session loads it (Q7); only the coordinator writes it, threads propose entries in their report-backs |
| Project settings (models) | the profile's model and effort tiers, enforced by hooks (an explicit model for money paths) |
| What Projects lacks | one writer to `main`, the merge gate, TDD and review rules, decisions by notification then option tool, cost discipline (watcher on change only, idle mode, rotation) |

## Scope

### A. The skills repository

- `skills/agent-coordinator/`: `SKILL.md` as a router (speaks the owner's language from the profile; never builds, reviews or pushes code) with references for starting and briefing threads, report-backs, watching (main-only watcher, hourly backstop, idle mode), decisions (whole-frontier rounds, notification, the option tool to collect; `grilling`, `domain-modeling` for terms and ADRs, the owner's `/grill-with-docs` and `/to-tickets`), reconciliation on every wake, merges and writers to `main` (merge-branch CI gate, batches), archiving and asking the owner to delete merged branches, pause all, restart and rotation (from durable state, no conversation summary; re-pointing report-backs, a report-back target that survives a rotation), the Artifact overview page, the Projects mapping, and the memory file.
- `skills/agent-thread/`: `SKILL.md` plus one reference per role: ticket (the default: dispatches the builder and fix-pass sub-agents, runs `code-review` itself, one report-back), builder (`tdd`, `diagnosing-bugs`, the TDD-order check), reviewer and re-review (`code-review`, two sub-agents, severities, head check; a re-review checks the earlier findings item by item in its Spec axis), fix pass (same session, head check, the ticket branch and never `origin/main`, red first), merge (`resolving-merge-conflicts`: code conflicts are resolved by the skill and the thread stops only on a failed proof; the profile's merge hooks, the gate, CI; reviewer and merge threads in a `git worktree`), research (`research`), prototype (`prototype`, with a pointer on the implementation ticket).
- `profile/TEMPLATE.md`: repository and environment, branch naming, pointers to the `docs/agents/*.md` files `/setup-matt-pocock-skills` writes (the profile never duplicates the tracker), the seams `tdd` tests at, gate and CI commands, merge hooks (for example makam's migration renumbering), money paths, model and effort tiers, pull-request policy (makam: never), owner language, decision protocol, memory file, the overview page, thread cap, context limit per role and same-session fix-pass limit, cadences, report-back format.
- `scripts/`: `sync.sh` (vendor these skills and the listed Matt skills at their pinned versions, with licences), a generic watcher that reads the profile, an optional brief generator.
- `evals/` with `skill-creator`: trigger evals (should and should-not prompts per skill), behaviour evals on dry-run briefs, and conformance evals (an agent never invokes an owner-only skill; a builder invokes `tdd`; a reviewer runs `code-review` with two sub-agents; an agent never reads an owner-only `SKILL.md` to carry out its steps and suggests the slash command instead).
- `README.md`: installation (with the owner's one-time `/setup-matt-pocock-skills`), the Projects mapping and Projects' documented limits, the mechanics outside the public docs and the reconciliation that backs them, that `agent-coordinator` is a consciously model-invocable `implement-spec`-style orchestrator unlike upstream's taxonomy, limits, licence; CI for the skills repository.

## Constraints (from the analysis, B.1)

- The orchestration skills carry no `disable-model-invocation`: the coordinator writes briefs and Routines write wakes. Whether a leading `/skill` expands in `create_session` and Routine prompts is untested: probe first.
- A checkout to a branch that predates the skills removes them: threads read their role reference before any checkout; reviewer and merge threads work in a `git worktree`.
- Recurring Routines fire at most hourly; one-off runs (`run_once_at`) are documented; binding into an existing session (`persistent_session_id`) is in the `create_trigger` tool contract but not in the public routines docs, which say each run creates a new session, so report-back also works through reconciliation (Q2); the GitHub proxy refuses branch deletion.

## Acceptance

- A fresh repository installs the skills and Matt's with one `sync.sh` command, the owner's one-time `/setup-matt-pocock-skills` and a filled profile, starts a coordinator session, and runs one ticket through builder, review and merge with report-backs, without Projects; the same run passes with Routine binding disabled, through reconciliation alone (Q2).
- The trigger, behaviour and conformance evals pass.
- Makam runs its next ticket on the skills; only then are the pasted role paragraphs removed.
