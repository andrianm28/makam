# How Perpanjangan verifies the Pemegang Hak

Status: resolved

## Question

When someone enters a Nomor Makam or the Almarhum's details, how does the platform prove they are the Pemegang Hak (documents uploaded, checked by Admin Lokasi, matched against imported records)? What if there is no Pemegang Hak on record, or it has passed to an heir?

Context from "YIEM's current assets and records": two cases. At a Lokasi Mitra, verify against the platform's own Pemegang Hak records (Admin Lokasi). At a DKI TPU, Perpanjangan is a Pengurusan: Admin YIEM files the IPTM extension on JakEVO for the ahli waris/penanggung jawab, so the question is which documents YIEM collects before filing.

Context from "Petak Makam lifecycle": at a Lokasi Mitra the Pemegang Hak sits on the Hak Pakai (which may cover a whole Kavling Keluarga), Perpanjangan is allowed until the end of the masa tenggang, and a change of Pemegang Hak (e.g. to an heir) is the Admin Lokasi action "Ganti Pemegang Hak" with documents and a history log.

## Answer

Decided with the user on 2026-09-25 (round 1 drafted by a parallel session, finished in the session that resolved "Petak Makam lifecycle"). Checked against [concept.md](../concept.md) Flow Perpanjangan (cari data → verifikasi → pilih periode → bayar sesuai tarif resmi → bukti bayar + surat bukti perpanjangan resmi) and [research §2.6](../research/cemetery-plot-regulation.md).

**A. Lokasi Mitra** (verified against the platform's own Hak Pakai)

1. **Lookup**: choose the Lokasi, then enter the Nomor Makam, the Nomor Kavling, or the Almarhum's name + year of death. Results show only the Almarhum's name(s), Nomor Makam/Kavling, status and end date; for a Kavling Keluarga the whole kavling is shown, since Perpanjangan covers all of it. The Pemegang Hak's details are never shown.
2. **Pemegang Hak on record**:
   - Quick path: OTP to the WhatsApp number recorded on the Hak Pakai (not the account's number, so it works with any login method). Correct OTP → choose **1–K terms** (price shown) → invoice, with no Admin Lokasi review. On payment the end date moves to old end + terms × N automatically; this counts as the Admin Lokasi's confirmation for Pencairan (refines "Money flow and revenue model", which paid out on the Admin Lokasi's confirmation).
   - Manual path (number changed or missing): upload KTP; the Admin Lokasi matches name/NIK and approves within 2 working days → choose terms → invoice.
3. **Pemegang Hak has died**: a combined Ganti Pemegang Hak + Perpanjangan. The heir uploads the Pemegang Hak's death certificate, proof of heirship (surat keterangan ahli waris from the Kelurahan, or a KK showing a spouse/child relationship) and their own KTP. The Admin Lokasi approves → Pemegang Hak changed (with history) → Perpanjangan invoice. Disputes between heirs are settled offline; the Admin Lokasi only records the outcome.
4. **No Pemegang Hak on record** (typically imported `Perlu Verifikasi`): a claim path. The requester uploads KTP, proof of relationship to the Almarhum (KK or a Kelurahan letter) and any old proof (receipt, certificate). The Admin Lokasi decides; if approved the requester becomes the Pemegang Hak, the flag clears, and the Perpanjangan follows.
5. **Who pays**: the request is always in the Pemegang Hak's name (via 2–4); the invoice link can be paid by anyone, and paying gives the payer no rights.
6. **When Perpanjangan is not offered** (the result is still shown, with a note instead of the button): perpetual Hak Pakai → "berlaku selamanya"; more than 3 months before the end date → "bisa diperpanjang mulai <tanggal>"; `Berakhir` → "hubungi Admin Lokasi" with the Lokasi's contact (never revived on the platform; the plot may already be sold as tumpang); `Dibatalkan` → not found.

**B. DKI TPU** (Pengurusan; Admin YIEM files on JakEVO)

7. **Identity**: the old IPTM is the proof. The applicant must be the ahli waris / penanggung jawab named on it, or an heir with the same proof of heirship as in 3. Admin YIEM checks the documents before filing, matching JakEVO's own rule so nothing is filed that the PTSP would reject. Grace period: 3 months after expiry (Perda DKI 3/2007).
8. **Documents**: uploaded by the Pemesan: KTP + KK, a photo of the old IPTM, and a surat kuasa generated by the platform (printed, bermaterai, signed and uploaded, or signed in front of the Petugas YIEM). YIEM (Petugas YIEM or Admin YIEM, per their KTP) is the proxy. The Petugas YIEM fetches the TPU's original surat pengantar and, if the PTSP asks, picks up the original old IPTM from the family, returning it with the new one.
9. **After issue**: the platform stores the new IPTM scan and expiry against a minimal TPU plot record (TPU + block/number + Almarhum + Pemegang Hak), reused for the next Perpanjangan and for reminders. The Pemesan receives the scan as the "surat bukti perpanjangan resmi".

**Amended by "Roles, accounts and access"** (2026-09-25): the Pemesan logs in with a WhatsApp OTP, so when the logged-in number equals the number on the Hak Pakai the separate Pemegang Hak OTP is skipped. Only the Admin Lokasi can change that number (after a KTP check).

**Amended by "Tagihan deadlines and refunds after Pencairan"** (2026-09-25): a Lokasi Mitra Perpanjangan Tagihan is due 3×24 h after issue; unpaid → Dibatalkan with no effect on the Hak Pakai; a manual-path approval stays valid 30 days for a new Tagihan.
