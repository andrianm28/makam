# Signed pull-based deploys: GitHub Deployment statuses, staging smoke test, production promotion and rollback

Status: in-progress
Blocked by: 71
Spec: Implementation Decisions > Architecture (CI/CD, production); ADR 0002 (second amendment of 2026-09-26); docs/ops/runbook.md

## What to build

Decided with the user on 2026-09-26 (rewritten after finding that GitHub Free offers no branch protection or environment approvals for a private repo). Deploys stay pull-based: the host pulls, verifies and deploys; CI never runs code on the host. Add image signing, deploy visibility in GitHub, a staging smoke gate, and owner-only production promotion and rollback.

## Acceptance criteria

- [x] **Signing**: after ticket 71's gate passes on `main`, CI signs the image digest with cosign (staging key pair; private key as a GitHub secret, public key installed on the host by `deploy/install-host.sh`). `makam-deploy` verifies the signature before `migrate` and refuses (distinct exit code, logged) any unsigned or wrongly signed image. Tests show an unsigned image is refused.
- [x] **Staging** follows the signed digest (not a mutable tag alone); the timer stays; each deploy step reports a GitHub Deployment and status (in_progress / success / failure, with the URL) using a fine-grained token limited to deployment statuses on this repository, stored on the host only.
- [x] **One digest for both environments**: the browser GlitchTip DSN (`NEXT_PUBLIC_SENTRY_DSN`) stops being a build argument and becomes a runtime value served to the browser; a test shows one image reports to the DSN of the environment it runs in.
- [x] **Staging smoke gate**: after a staging deploy, a short Playwright smoke test runs from a hosted runner against `https://dev.makam.co.id` (health, home, Masuk page); its result is recorded against the digest, and promotion refuses a digest whose smoke test did not pass.
- [x] **Production promotion**: a `workflow_dispatch` "Promosikan ke produksi" that refuses unless `github.actor` is the repository owner, requires the release tag typed again, requires the digest to be the one deployed and healthy on staging, signs it with a separate **production** key, and creates `vYYYY.MM.DD-N` with generated release notes. The production host accepts only production-signed images.
- [x] **Rollback workflow**: owner-only `workflow_dispatch` re-promoting an earlier released digest (same signing), plus the by-hand `makam-deploy --digest` path in the runbook.
- [x] **Production safety in `makam-deploy --env prod`**: `pg_dump` snapshot before `migrate`, kept on the host with rotation and never copied off it (decided 2026-09-27, ticket 64: in v1 nothing goes off-host; off-host copies are v2, with the S3 work blocked by 03); failed `migrate` → nothing restarted; failed `up` or `/api/health` → automatic rollback to the previous digest and a failure status. Migrations are never rolled back automatically.
- [ ] **Releases**: CI uploads source maps to GlitchTip for each image (release-scoped token as a GitHub secret) and each deploy creates a GlitchTip release for the commit. **Implemented, never run**: the build-time release and the `sourcemaps` block in `next.config.ts`, ci.yml's `sourcemaps` job (`scripts/ci/upload-sourcemaps.sh`) and `deploy/bin/makam-glitchtip-release` are all in and tested. Both still need a GlitchTip auth token that does not exist yet: the `GLITCHTIP_AUTH_TOKEN` secret plus the three `GLITCHTIP_*` variables for CI, and `MAKAM_GLITCHTIP_TOKEN` in each env file on the host (runbook, "Source maps and releases"). Without a token the job warns and the release is a logged no-op, so nothing about a deploy changes; until one is created, GlitchTip shows minified JavaScript.
- [x] **Concurrency**: signing, promotion and rollback run in groups that are never cancelled mid-way.
- [ ] **Rehearsal**: `makam-prod` deployed once through the promotion on 127.0.0.1:3100 with sandbox keys and no nginx change; a forced failing healthcheck shows the automatic rollback; an unsigned image is refused. **Not run**: the promotion and the signature check both need real cosign key pairs, which do not exist yet (see `## Comments`). Both behaviours are covered by `tests/tooling/makam-deploy.test.ts`, which drives the real scripts against fakes.
- [x] Runbook: signing keys (where they live, how to rotate), approving a promotion, rolling back, pausing deploys, reading deploy results in GitHub and `deploy.log`.

## Comments

- 2026-09-28 — **The signing action could never have worked, and two of its three faults were a file that should never have existed.** `.github/actions/cosign-sign/action.yml` wrote the private key to `$HOME/.sigstore/cosign.key` with mode `0600` and the passphrase to `cosign.password`, then `docker run`ned the cosign image. Three things were wrong with that, and none of them was the key:

  - **The key was unreadable.** The cosign container runs as **uid 65532**, so a `0600` file owned by the runner is a `permission denied` for the one process that needs it.
  - **The passphrase never arrived.** cosign v2.6.1 reads it from `COSIGN_PASSWORD`, a TTY, or stdin. The `docker run` sent neither `-e` nor `-i`, and **`cosign.password` is not read by cosign at all** — there is no `--password-file` in that version. The key is encrypted, so this alone made every run fail.
  - **The key was left behind on failure.** The `rm` was the last line, so it ran only when `docker run` succeeded.

  **The fix removes the file rather than repairing it.** cosign reads `COSIGN_PRIVATE_KEY` and `COSIGN_PASSWORD` from the environment, so the key now goes into the container that way and **nothing touches the runner's disk** — which retires the permission fault, the passphrase fault and the leftover-file fault at once, rather than three separate patches to a design that did not need a file.

  **One guard was added that nobody asked for: only a digest may be signed.** Every caller passes `needs.deploy-gate.outputs.ref`, which is pinned, so this changes nothing today — but the action itself did not check, and a tag signed now and pulled later is exactly the window this design exists to close. The window was closed by caller discipline rather than by the signer, which is the fragile way round. The action now refuses a reference without `@sha256:` and says why.

  **How this was found matters more than the fix.** A read-only audit was dispatched specifically because the action was about to execute for the first time, and it could answer "has this ever run?" — it has not: across the last forty runs the `sign` job appears five times and **every one died at its second step**, with the cosign step `skipped`. So nothing about this action had ever been exercised, and the first three faults would each have stopped the deploy in turn, each looking like a different problem. **A workflow nobody has run is not a workflow that works slowly; it is one that does not work at all**, and the only way to know which is to read it before it is needed.

  The failure direction is right throughout, and worth saying: every path fails hard, and the host verifies the digest's signature again itself (`deploy/bin/makam-verify-image:56`, exit 77, called from `makam-deploy:253`). So the risk here was always **red**, never **wrong** — which is the property that has to hold on the signing path.

- 2026-09-28 — **And the rollback path has the same shape of problem: never run, and wrong in a way that is quieter than failing.** `gh run list --workflow=rollback.yml` returns `total_count: 0`. Two defects, both found by reading and neither observable until it is needed.

  **It would always refuse.** The host records `ref=sha-<hex>` (`makam-deploy:221`, `makam-deploy-status:81`), while the workflow compares `.ref == $sha` against `targetCommitish` with a **bare** SHA (`rollback.yml:52-54`). Those never match, so the lookup returns nothing and the workflow refuses. Fail-closed, which is the right direction — and also **useless**, since a rollback that always declines is not a rollback. It is being masked today by there being zero production deployments at all, so the lookup is empty either way and nobody would learn this from watching it.

  **And it can roll back to a digest that is not the one asked for.** `targetCommitish` may carry a **branch name** rather than a SHA, and `select(.ref == ...)` (`:54`) then takes the **first** matching digest — which may belong to a different release. That is a wrong production image rather than a red run, and it is the failure mode worth naming: the second finding is worse than the first, because the first is a wall and the second is a wrong door.

  **What is sound, and worth saying so:** the workflow's `actions/checkout` fix is correctly placed at `:68`, before both local actions, and the two `run:` steps before it need no tree. The host does verify the signature it is about to deploy (`makam-deploy:253`, exit 77), so the missing verify in the workflow is safe today **only because the host refuses an unsigned digest** — that is a second line of defence, not a design. There is no down migration; `makam-deploy` re-runs `migrate` (a no-op) and new columns simply remain, which expand/contract (`docs/adr/0002:34`, runbook) makes safe, and the workflow says so at `:98` rather than claiming a safety it does not have. The operator types a **tag**, not a digest (`:15-18`), plus a reason (`:19-22`). No job declares an `environment:`, so there is no approval or secret protection on the one path that changes production.

  Taken with the `promote.yml` audit above, the picture is: three production workflows, **none of which has ever executed**, all of which contain at least one defect visible only on first use — a staging signature that is never verified, a promotion that can deploy after reporting failure, an approval ADR 0002 promises and no `environment:` implements, a rollback lookup that can never match, and a rollback that can select the wrong digest. **None of this touches the staging deploy**, which goes `sign` then `makam-deploy --env staging` and never enters `promote.yml`. All of it should be settled before production takes its first digest.

- 2026-09-28 — **A read-only audit of `promote.yml` found a hole in the production path, found only because the workflow has never run.** `gh run list --workflow=promote.yml` returns `total_count: 0`, so every claim below is about code that has never executed. The sequence is: take the most recent **staging** digest from the Deployment record (`:62-65`), require that run and a staging smoke test naming that digest to have succeeded (`:71`, `:76`), then **sign it with the production key** (`:102-103`) and publish a release. **There is no `cosign verify` against the staging key anywhere.** So a digest that was never signed with staging's key — or was signed by something else — is promoted, and `makam-verify-image --env prod` accepts it, because it only checks the production signature, which the promotion has just created for that same digest. The verification on the host is real; it is being asked the wrong question.

  **The second finding is quieter and worse.** If `gh release create` (`:116`) fails **after** the signing step has succeeded, the digest is already production-signed. The host timer follows `:latest` and `makam-deploy` deploys it **with no release** (`:234`). So a promotion that reports failure can still reach production. That is a failure mode where the red run and the deployed thing disagree, and nothing in the workflow prevents it.

  **And the approval ADR 0002:31 promises is not implemented.** No job in `promote.yml` declares an `environment:`, so the production approval that the ADR records is not enforced by anything. The staging side of the flow is explicit (`environment=staging`, `:62`); the production side is implied only by which secret's name appears in the step (`:102`).

  **None of this blocks the staging deploy.** The staging path is `sign` plus `makam-deploy --env staging` and does not go through `promote.yml` at all, so a UAT on staging is unaffected. This is recorded as a gap on this ticket rather than fixed here, because it is a design decision about where verification belongs in a two-key setup, and because fixing it is not the orchestrator's to make in the middle of a deploy. What should be settled before production ever gets a digest: **whether the staging signature is verified before promotion or is simply not required**, and if not required, why the host has a staging key that verifies nothing.

  Credit where due: the `actions/checkout` fix applied to this workflow too, and its composite actions are correctly preceded by it — the defect that silently killed `sign`, `sourcemaps` and `rollback` is not present here. The host's own behaviour is sound: a failed migration leaves the old image running, a failed `up` rolls back, and every action in the workflow is pinned by SHA or digest.

- 2026-09-28 — **The red `main` this ticket left behind, and the one-line fix, recorded on the way to it.** `cd70da0` added `.github/actions/ghcr-login/action.yml`, a composite action whose step read `password: ${{ secrets.GITHUB_TOKEN }}`. A composite action is validated as its own manifest, and the `secrets` context is **not a recognised named-value there**, so GitHub refused to load the action at all: `TemplateValidationException: The template is not valid ... Unrecognized named-value: 'secrets'`. Four workflows use this action — `ci.yml`, `promote.yml`, `rollback.yml` and `image-retention.yml` — so **every** job that logs in to ghcr failed in **0 seconds**, and the four jobs downstream of one were skipped: `Build image`, `Migration upgrade` (which is the expand/contract check every migration must pass), `E2E`, `Image scan and SBOM` and `Deploy gate`. The consequence is not cosmetic: **no image could be built, so nothing could be deployed, and e2e could not run at all.**

  This was red on `main` from `0a91a78` at 2026-09-27 18:42 UTC — before this orchestrator session pushed anything. The six CI runs from that time forward all failed, and the failures on the two commits it went on to push were inherited, not caused.

  **The fix is one line: `${{ github.token }}`.** GitHub's own documentation settles it: `secrets.GITHUB_TOKEN` is valid in a *workflow*, and separately, "an action can access the GITHUB_TOKEN through the `github.token` context even if the workflow does not explicitly pass the GITHUB_TOKEN to the action". The `github` context is available inside a composite action's step `with:`, so `github.token` is the same workflow token under a name the manifest accepts. Least privilege is unaffected: what the token may do is still only the job's own `permissions` block, which is where the action's own description says it lives. The nine other `secrets.GITHUB_TOKEN` uses in `.github/` are all in *workflows*, where the context is valid, and are left alone — verified by checking that no `action.yml` under `.github/actions/` still uses it.

  **The lesson is the orchestrator's, and it is the one worth keeping:** every merge this session was verified by `typecheck && lint && build && test:shared` on a merge worktree, all green, and none of that would ever have caught a broken workflow manifest. The check that would have caught it is one `gh run list` — thirty seconds — and it was not run until the owner asked whether a deploy was happening. **A green local suite is evidence about the code and about nothing else.** The deploy path is a separate system with its own failure modes, and a session that treats "verified" as "ready" is reasoning past its evidence. Every merge from here on waits for `main` CI, not for the local chain.

It *generates* the maps and the debug ids and uploads **nothing** (`sourcemaps.disable: "disable-upload"`, `deleteSourcemapsAfterUpload: false`), so a token can never reach an image layer; ci.yml's new `sourcemaps` job pulls the pushed image, takes `/app/dist/sourcemaps` out of it and runs `sentry-cli sourcemaps upload` with the secret. `scripts/collect-sourcemaps.mjs` moves the maps out of `.next/static`, which the web server serves, so the source is not published with the site. A test shows the upload only ever targets the configured https GlitchTip and never sentry.io, that nothing is sent without the token, and that a `SENTRY_URL` that is not https is refused.
  - **A GlitchTip release per deploy**: `deploy/bin/makam-glitchtip-release` (installed by `install-host.sh`) creates the release for the running commit, after the health check, best effort: no token, GlitchTip down, or a release that already exists is a logged no-op and **never** a failed deploy (locked by tests). Only the *browser* source maps are uploaded; server and worker maps still are not (the worker bundle's `dist/*.mjs.map` stays unused) — recorded in the runbook, not in an AC.
  - **The migration baseline is honest**: `deployed-release.ts` and its test now only accept a deployment whose own state is `success`, and the `migrations` job walks the newest twenty deployments per environment, so a refused or rolled-back attempt is skipped instead of becoming the baseline (it agreed with the promotion's rule and not with the code). `statuses_url`, which was parsed and never used, is gone.
  - **Exit codes tell the two failures apart**: a deploy that fails and rolls back cleanly exits **1**; only a roll back that failed as well (or a first deploy with nothing to roll back to) exits **2**. `makam-deploy`'s header said 2 for both. Three tests in `tests/tooling/makam-deploy.test.ts` now say which is which.
  - Checked and left alone (the review found them correct): the signature is verified before `migrate`; a roll back never runs `migrate`; the smoke gate and the promotion both refuse without a passed smoke test; `cancel-in-progress: false` everywhere a deploy step runs.
- 2026-09-27 — **Standards axis, second pass** (same branch, not merged). Three hard findings, all closed:
  - **cosign ran from a mutable tag** in three workflows, and that container reads a cosign *private key*: `sigstore/cosign:v2.6.1` is now pinned by digest, and the 14-line block is one composite action (`.github/actions/cosign-sign`) that ci.yml, promote.yml and rollback.yml each call with their own key pair, so the pin exists in one place. It still refuses without a key.
  - **The browser DSN was frozen at build time** (AC 3, and the reason `staging-banner.tsx` gives). `RootLayout` read `NEXT_PUBLIC_SENTRY_DSN` while rendering, but `/` and `/_not-found` are statically rendered: the value went into the HTML at build time, where the image has no environment at all, so in the real image the browser had `""` forever. The DSN is now served per request by `GET /api/browser-config` (`connection()`, `no-store`) and the browser starts the SDK with the answer (`instrumentation-client.ts`, `components/browser-sentry.tsx`). Same design as the staging banner: a static page cannot know its environment, so the browser asks. `/` and `/_not-found` stay `○ (Static)`: a build shows `.next/server/app/index.html` with no DSN in it at all, and the `@smoke` spec now *proves* that (no DSN in the served HTML, the served value and the browser's value identical, a real DSN required on the hosted hosts instead of skipped when empty).
  - **The `migrations` job fetched tsx from the registry** to read the baseline, before `setup-node` and `npm ci`. Node and the dependencies now come first and the step runs `npx --no-install tsx`, so the code that chooses which image to upgrade from uses this repository's own pinned tsx.
  - Smells: the cosign duplication is the action above; the `image` job's comment about who moves `latest` now says `sign`, not `deploy-gate`; the compose `image:` error no longer offers `MAKAM_DEPLOY_REF` as an option (that variable takes the whole expression, so it is never what the error asks for).
  - Verified green: lint, typecheck, `npm run build` (the static-HTML check above), and the full `npm run test:shared`.
