# Encrypted Postgres backups to S3 Jakarta and restore test

Status: resolved
Blocked by: 07
Spec: Implementation Decisions > Architecture (backups); ADR 0002

## What to build

Split from ticket 07 on 2026-09-25. Daily client-side-encrypted backups of the `makam-staging` and `makam-prod` Postgres to the `makam-prod-backups` bucket in `ap-southeast-3`, and a scripted restore test.

## Acceptance criteria

- [ ] Daily backup (pgBackRest with `repo-cipher-type`, or wal-g with libsodium), encrypted client-side; WAL/retention settings documented in the repo.
- [ ] A restore script restores the latest backup into a scratch Postgres and runs a row-count check; it has been run once and the result recorded in `## Comments`.
- [ ] Tests: the restore script is exercised in CI against a local backup of the test database.
- [ ] The runbook in `docs/ops/` gains backup and restore sections.

- 2026-09-26 — Research (read-only; no code, containers or AWS touched). **Recommendation: pgBackRest 2.59.1**, not wal-g.
  - Why: PG 18 supported since v2.55 (Apr 2025), current 2.59.1 (Aug 2026) is in the same PGDG `trixie-pgdg` apt repo our `postgres:18.6` image is built from (`2.59.1-1.pgdg13+1`), so it installs version-matched with one `apt-get`. Built in: client-side `aes-256-cbc` encryption, time-based retention plus expire after every backup, `verify`, `info --output=json` for monitoring, backup annotations, block incremental, restore `--archive-mode=off` for throwaway restores, and an upstream least-privilege S3 policy. wal-g (v3.0.9, Aug 2026) has good libsodium encryption, but PG 14–18 only entered its integration CI on 2026-08-25 (PR #2504, after the last release), retention is a separate `delete retain` job, and its docs warn that retention ordering breaks after major upgrades unless you pass `--use-sentinel-time`. Caveat: pgBackRest's homepage now lists Crunchy Data as a *past* sponsor. Releases continue, but re-check this at each major PG upgrade.
  - **Where it runs: in the Postgres container, not a sidecar.** `archive_command` runs inside the Postgres server process, so the binary must be in that image whichever tool we pick. A sidecar would need pgBackRest's TLS server and a repo host, which is more moving parts on one VPS. Plan: `deploy/postgres/Dockerfile` = `FROM postgres:18.6@sha256:5a5a…` + `apt-get install pgbackrest=2.59.1-1.pgdg13+1`, pinned by digest like every other image. In `docker-compose.prod.yml`, the `postgres` service gets `command: postgres -c archive_mode=on -c archive_command='pgbackrest --stanza=makam archive-push %p' -c archive_timeout=300` (RPO ≈ 5 min; changing `archive_mode` needs one restart). It also gets a separate `env_file` (`/opt/makam-v1/<env>/pgbackrest.env`, 0600, **not** the app's env file) and a `pgspool` volume. Backups run from host systemd timers through `docker compose exec -u postgres postgres pgbackrest …`, so they stay inside Postgres's existing 2 CPU / 2 GB limit.
  - **Config** (as `PGBACKREST_*` env or `pgbackrest.conf`): `pg1-path=/var/lib/postgresql/18/docker`, `repo1-type=s3`, `repo1-s3-bucket=makam-prod-backups`, `repo1-s3-region=ap-southeast-3`, `repo1-s3-endpoint=s3.ap-southeast-3.amazonaws.com`, `repo1-path=/pgbackrest/<env>` (one prefix per env), `repo1-s3-key`/`-key-secret`, `repo1-cipher-type=aes-256-cbc`, `repo1-cipher-pass=$(openssl rand -base64 48)` (one per env; ticket 03 keeps the offline copy; **losing it makes every backup unreadable**, and it cannot be changed after `stanza-create`), `repo1-bundle=y`, `repo1-block=y`, `compress-type=zst`, `process-max=2`, `archive-async=y` + `spool-path=/var/spool/pgbackrest`, `start-fast=y`. Retention: `repo1-retention-full-type=time`, `repo1-retention-full=35` for prod and `=7` for staging. WAL is expired along with its backups, so PITR covers the whole window. Setup: `stanza-create` then `check`.
  - **Schedules (WIB, `OnCalendar=… Asia/Jakarta`)**: full backup Sunday 02:00; `diff` Monday–Saturday 02:00; WAL continuous; `verify` monthly; staging the same but full backups monthly. Before each prod migrate, ticket 72's `makam-deploy` keeps its local `pg_dump -Fc` (fast undo path, portable across majors) and **also** runs `pgbackrest backup --type=incr --annotation=predeploy=<tag>`. That makes the off-host part of "pg_dump before migrate" a named PITR point, with no second encryption scheme for dump files. Open question 4 covers whether the dump itself must also go off-host.
  - **IAM** (the upstream sample, narrowed): one user per env (`makam-backup-prod`, `makam-backup-staging`), plus a read-only `makam-restore-test`. Skeleton for prod:
    `{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":"s3:ListBucket","Resource":"arn:aws:s3:::makam-prod-backups","Condition":{"StringLike":{"s3:prefix":["","pgbackrest","pgbackrest/prod","pgbackrest/prod/*"]}}},{"Effect":"Allow","Action":["s3:GetObject","s3:GetObjectVersion","s3:PutObject","s3:PutObjectTagging","s3:DeleteObject"],"Resource":"arn:aws:s3:::makam-prod-backups/pgbackrest/prod/*"}]}`
    Deliberately withheld: `s3:DeleteObjectVersion` and every `s3:PutBucket*`/`PutLifecycle*` action. With versioning on, a stolen host key can only add delete markers. For ticket 03, set a lifecycle rule "expire noncurrent versions after 14 d" on the bucket, which also answers its "Object Lock or lifecycle" choice. Object Lock is optional: it does not block delete markers, so pgBackRest's expire keeps working. The restore user gets only `ListBucket` + `GetObject` + `GetObjectVersion` on both prefixes, so a restore test cannot write to the repo. Note that **ap-southeast-3 is an opt-in region**: it must be enabled on the account first.
  - **Restore test** (`deploy/bin/makam-restore-test --env prod|staging`, weekly on Monday 04:00; also run once by hand and recorded here, per the acceptance criteria):

    4. Log the duration (RTO), the backup label and the counts to the journal (tag `makam-restore`).
    Disk: the host has ~20 GB free (80 % used), so the script refuses to start unless free space > 2 × DB size.
    CI: the same script runs against a `repo1-type=posix` local repo of the test database (no S3 in CI).
  - **Alerting**: GlitchTip uptime monitors of type **Heartbeat** (built in; alerts email the linked project).
