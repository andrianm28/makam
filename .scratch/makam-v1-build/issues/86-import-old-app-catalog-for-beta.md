# Import the old app's cemetery catalog as beta data

Status: resolved
Blocked by: 12
Spec: Release plan (beta UAT push); ADR 0002 (beta UAT amendment); decided with the user 2026-09-26

## What to build

The v1 beta for UAT is seeded with the frozen Laravel app's cemetery catalog (read-only from its database at /home/ubuntu/makam-app's stack), so testers see real-looking Lokasi. Only non-personal catalog data comes across.

## Acceptance criteria

_Rewritten 2026-09-27 after the research of the same day (see `## Comments`): the original lines promised what the old app's data cannot give. The lines below are what the tool does._

- [x] An ops command (like `seed:admin`) reads, read-only, a **catalog export file** the old app's owner produced with one documented `psql` query (never a connection of its own): name, address, city, coordinates / Google Maps URL, the source's own facility labels, and its indicative price ranges. It creates Lokasi Mitra and their Jenis Makam with a first tariff version **only where the source holds a real price**; a range the source only estimated is reported and asked about, never entered as a Tarif.
- [x] **Photos are not imported.** The old app's `primary_photo_path` is a storage path of four stock photos reused across every row (research §1.4: "none of the four photos depicts any of these cemeteries"), and v1 keeps photos in the private FileStore written by a Kunjungan Verifikasi or a Blok site plan. The beta is on free stock photos (ADR 0002); copying files out of the old app is a separate decision.
- [x] **Every imported Lokasi Mitra is marked as example data on the record** (`lokasi_mitra.data_contoh`, set through `lokasi.tandaiDataContoh` with a reason, audited as `lokasi.tandai_data_contoh`), and the Lokasi module refuses to publish a marked one (`data_contoh_tidak_bisa_diterbitkan`) and leaves it out of every public read whatever its status says. An import verifies nothing, so nothing it creates may be listed; the owner clears the mark by hand, with its own reason, once a row is real. Where the **source** itself froze a row as example data (the `Jl. Contoh` address / `(pemakaman contoh)` name markers) the report says so by name as well.
- [x] It never reads or copies users, orders, payments, phone numbers, emails, documents or any personal data. Two guards, in this order: a personal **column** anywhere in the document refuses the export by name before a value is read, and a free-text **value** that looks like personal data (an email, an Indonesian phone number) or embeds a document (`{`/`[`) refuses it too. Tests prove both, and that a rejected export writes nothing.
- [ ] Idempotent (running it twice doesn't duplicate; keyed on the source's own code in `katalog_lama_lokasi` / `katalog_lama_jenis_makam`); a bind and its Entri Audit are one transaction, so no code is ever bound with nothing in the Audit Log about it. Development and test always; **staging (the beta's own environment) only with the named allowance `--izinkan-staging`**, refused by default and named in the reason of every write it makes; production never, allowance or not. Every write is audited.
- [x] Imported Jenis Makam whose all-in total exceeds the Rp 10 juta cap are kept but not listed (spec, Billing).
- [x] Runbook section, with the export query held to the export contract by a test (`tests/tooling/katalog-lama-runbook.test.ts`: every contract field is exported, and a fact field may not be a constant); the old app's stack and data are never modified.

### What the owner has to prepare (the old app's `makam_beta`)

**The research of 2026-09-27 answers most of this, and the answer changes the ticket.** Two things the ticket did not know when it was written:

1. **The old app's catalog is 100 % fabricated.** `makam_beta` holds 10 `cemeteries` rows, every one of them an example row: addresses starting `Jl. Contoh`, names ending ` (pemakaman contoh)`, prices derived from the row index (`price_min = 3.000.000 + index × 500.000`, `price_source = 'Estimasi internal (data contoh)'`). The four "real" TPUs named in the old app's own migrations were never rows in any database (research §1.5). So AC 1's "so testers see real-looking Lokasi" **cannot be met from the source the ticket names**; the import will faithfully bring across ten synthetic cemeteries, and its report says so in as many words ("Data contoh di aplikasi lama (10 Lokasi) … Katalog ini bukan data makam sungguhan").
2. **There is a better catalog in this repo already**: `.scratch/makam-v1-build/research/dki-tpu-list.csv`, 78 real DKI TPUs with address, coordinates, a data source and a `menerima_makam_baru` flag (research §1.6). **Ticket 43 already has its own ticket for feeding those in**, so importing them here would collide with it. This is the owner's decision, and it is bigger than this ticket: either the beta's Lokasi come from the 78 real TPUs (and ticket 86's importer is pointed at that CSV instead of `makam_beta`), or UAT testers see ten fabricated cemeteries. **The tool in this ticket serves both**: it is a read-only importer of a catalog export into Lokasi Mitra, Jenis Makam and tariffs, and nothing in it knows where the catalog came from.

What the owner still has to do, either way:

1. **Run the export query** (runbook, "Importing the old app's cemetery catalog"), one JSON file per run. The column names are now the old app's real ones, so it is a copy-paste; the three things to check are the `launch_cities` join (the old `city` is a code), the hand-mapped `facilities` (free text there, a closed list here) and the `pengelola` fallback for a null `operator_name`.
2. **Decide the prices.** Nothing in `cemetery_packages` is a transactable price (research §1.4), so every Jenis Makam comes through the import as refused (`harga_belum_dapat_dimasukkan`) with its indicative range reported, until someone types a real `hargaHakPakai` + `masaHak` (+ `hargaPerpanjangan` for a fixed term) into the export. The 78 real TPUs in the CSV have no prices at all, so this decision is needed for them too.
3. **Photos are not imported.** v1 keeps a Lokasi Mitra's photos in the private FileStore, written by a Kunjungan Verifikasi (ticket 15) or a Blok's site plan (ticket 13); the old app's `primary_photo_path` is a storage path of four stock photos reused across all rows, and the beta is on free stock photos (ADR 0002). Copying real cemetery photos out of the old app is a separate decision, and there are none to copy.

### Open questions for the owner

1. **Which catalog does the beta show** — the old app's ten fabricated rows, or the 78 real DKI TPUs already in this repo (and does that make ticket 43 the owner of the import, with this ticket only the tool)? Everything else here works for either source.
2. **How does the old app mark "belum tayang"?** Answered by the research: there is no such column. `publication_status` (`draft` / `published` / `unpublished`) is the public-directory axis, and the "this is example data" markers are a second, separate axis. The export carries the status, the report quotes it, and nothing else is done with it — because in v1 a Lokasi Mitra is Belum Tayang until the publish gate (Kunjungan Verifikasi, agreement, Jam Operasional, "tarif diperiksa"), which no old row can satisfy. **Should the beta show these Lokasi in the public directory at all**, and if so, how may a beta Lokasi pass the publish gate without inventing a Kunjungan Verifikasi?
3. **Old prices against the Tarif versions already in force in v1.** v1 never rewrites a price that was already in force, so an old price with a `berlakuMulai` before today is refused (`harga_berlaku_sudah_lampau`) and reported. The owner decides per Lokasi: enter it as today's version (what the importer does when there is no `berlakuMulai`), or date it from the day the beta's testers should see the new price.
4. **Settled (2026-09-27, the re-review): the escape hatch exists, so the import runs where the beta runs.** `--izinkan-staging` is a named flag, refused by default (`Ditolak: di staging perlu allowance --izinkan-staging`), and every write it makes carries `impor katalog aplikasi lama (staging, --izinkan-staging)` in its Entri Audit reason, so the Audit Log of every row created on the beta's own environment says so; `production` is refused outright, allowance or not (`Ditolak: import-katalog-lama tidak pernah jalan di production.`, checked before anything else). Tested: staging without the flag refused, production with it refused, staging with it writes and every non-null reason names the allowance. **There is no dump from a development stack in the procedure any more** — the runbook's "Dry run, then write" runs the two commands against the environment in question, the second one with the allowance, and nothing else. The AC as originally written ("seeded from the old app's catalog") can therefore hold on `makam.co.id` itself. **What still cannot happen there**, and is a separate decision rather than a gap in the tool: an imported Lokasi stays `belum_tayang` and `data_contoh`, so the beta's testers see it in the staff area, not in the public directory — see open question 2, which is the only one that now stands between the importer and a tester-visible Lokasi.
5. **Petak Makam / Denah / Kavling Keluarga** are not imported. The old app has `cemetery_blocks` (a `capacity`, no grid) and `grave_plots` (bulk-generated slots, two blocks and nine plots in `makam_beta`), which v1's Denah builder cannot be told from, and "Kavling Keluarga" does not exist in the old app at all (research §1.6). If UAT testers need a Denah, that is a follow-up ticket, and the 78 real TPUs would need their Blok data from somewhere else anyway.
