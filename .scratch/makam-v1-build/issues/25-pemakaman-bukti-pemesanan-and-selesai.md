# Catat Pemakaman, Bukti Pemesanan and Saat Duka Selesai

Status: ready-for-agent
Blocked by: 19, 23
Spec: Domain modules > 5. Inventory (Pemakaman); 6. Pemesanan (Saat Duka statuses, Selesai); 10. Billing (pay-after clock, Documents); 16. Scheduler ("Catat Pemakaman" prompts); Testing Decisions > End-to-end 1; stories 36, 37, 119

## What to build

The Admin Lokasi records the Pemakaman (date, Petak, layer), prompted by a Catat Pemakaman row the day after the planned date. Recording sets the order Dimakamkan, starts the Hak Pakai tenure clock (first Pemakaman), and starts the pay-after Tagihan clock from the recorded date. When the Tagihan is Lunas a Bukti Pemesanan is issued in the Lokasi Mitra's name (right only, no amounts) and the order becomes Selesai. The Pemesan's order page shows the order status and the Tagihan status as a separate badge. Add the first Playwright critical path end to end.

## Acceptance criteria

- [x] Catat Pemakaman row (Antrean Lokasi, Lainnya) appears the day after the planned burial date via a tick, and closes when the Pemakaman is recorded.
- [x] Recording a Pemakaman sets the order Dimakamkan and, for a fixed-term Jenis Makam, sets the Hak Pakai end date = first Pemakaman + tenure.
- [x] The pay-after Tagihan becomes Lewat Jatuh Tempo 3×24 h (Lokasi policy) after the **recorded** burial date; the Tagihan is not reissued if the recorded date differs from the planned one (its printed due date stays).
- [x] On Lunas: Bukti Pemesanan `BPM/YYYY/NNNNNN` (Lokasi, Petak Makam, Pemegang Hak, masa Hak Pakai; PT JKP header; proves the right in the Lokasi Mitra's name) is issued, its link sent by email (for an order with no email, CS shares it by hand); the order becomes Selesai (= Lunas + Bukti Pemesanan issued).
- [x] Order status and Tagihan status are shown separately (e.g. Dimakamkan + Belum Dibayar).
- [x] Tests: "Saat Duka Tagihan becomes Lewat Jatuh Tempo 3×24 h after the recorded Pemakaman"; payment before burial (Lunas, then Dimakamkan → Selesai) and after; Catat Pemakaman prompt timing; Playwright: Pilih makam list → email Kode Masuk → Admin Lokasi confirmation → payment (signed fake webhook) → Bukti Pemesanan.

- 2026-09-27 — **A reading the AC settled, and it is the one the tests pin.** "On Lunas" (AC 4) and "Lunas, then Dimakamkan → Selesai" (AC 6) can only both hold if the Bukti Pemesanan is issued where the *second* of the two facts lands: a payment settles after the burial is recorded (Billing's payment effect, in the payment's own transaction), or the burial is recorded after the payment (the recording step, in the burial's transaction). One function serves both (`terbitkanBukti` in `src/domain/pemesanan/efek-bukti-pemesanan.ts`), so a Bukti can never be issued twice and a number is never spent twice. Consequence worth naming: a paid order whose burial is not yet recorded has **no** Bukti Pemesanan, because the document names the Hak Pakai's term and that term starts at the first Pemakaman — the order is Dikonfirmasi, not Selesai.
