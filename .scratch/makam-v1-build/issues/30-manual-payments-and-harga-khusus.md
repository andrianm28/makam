# Manual payments, direct payment to the Lokasi and Harga Khusus

Status: ready-for-agent
Blocked by: 25
Spec: Domain modules > 10. Billing (Payment: manual, direct, Rp 0); 11. Payouts (Harga Khusus, Dibayar langsung); stories 134, 163, 164

## What to build

The payment paths outside the provider. Admin Platform marks a Tagihan paid by hand (Transfer manual / Tunai) with an uploaded proof. The Admin Lokasi records "Dibayar langsung ke Lokasi Mitra" with proof when a family paid the Lokasi directly; Admin Platform can reverse it. Admin Platform sets a Harga Khusus on an order, which cancels and reissues the Tagihan with a negative "Penyesuaian Harga Khusus" line; a resulting Rp 0 Tagihan is Lunas at once. Each path issues exactly one Bukti Pembayaran and runs the same downstream effects as a provider payment.

## Acceptance criteria

- [ ] Manual payment requires a proof file; the Bukti Pembayaran shows method Transfer manual or Tunai; audited.
- [ ] Direct payment: the Bukti Pembayaran reads "diterima oleh Lokasi Mitra X"; it records that no tariff Pencairan is due and a platform-fee Potongan is owed (consumed by ticket 32); reversible by Admin Platform only, audited.
- [ ] Harga Khusus: Admin Platform only, with a reason; the Tagihan is reissued (never edited) with a negative line. Admin Platform may enter on the order the partner share (the amount the Lokasi Mitra agreed to bear) with a required note; default 0, in which case the Operator bears the whole reduction (from the Biaya Layanan Platform first, then its own funds). A non-zero partner share lowers that order's Pencairan (ticket 32); audited.
- [ ] A Rp 0 Tagihan becomes Lunas immediately with method "Tanpa pembayaran (Harga Khusus)".
- [ ] Each path fires the downstream-effect registry once (e.g. Bukti Pemesanan issued).
- [ ] Tests: each method's Bukti Pembayaran wording; direct-payment reversal; Harga Khusus reissue and Rp 0 waiver; partner share requires a note and defaults to 0; immutability preserved.

## Comments

- 2026-09-26 — From ticket 18 review (user decision): a reissued Tagihan keeps the original due date. So Admin Platform cannot reissue (e.g. add a Harga Khusus to) a pay-first Tagihan that is already past its due date: the action is refused with a clear message, and the order is placed again instead. A Rp 0 Tagihan is already Lunas at issue (ticket 18).
- 2026-09-26 — User decision: online payment in v1 is QRIS only (Bank Indonesia caps QRIS at Rp 10.000.000 per transaction); a Tagihan above that shows no Bayar button but the Operator's bank account for a transfer, recorded by Admin Platform as a manual payment (ticket 30); no Virtual Account in v1.
- 2026-09-26 — User decision (supersedes the same-day manual-transfer note): v1 takes no order whose Tagihan would exceed Rp 10.000.000 (QRIS cap); see spec, Billing. No manual-transfer path for amounts above it in v1.
- 2026-09-28 — Builder readings and decisions (ticket 30 built on `origin/main` at `db84bd7`, after ticket 25):
  - **Manual and direct payment live inside Billing** (`src/domain/billing/pembayaran-staf.ts`: `catatPembayaranManual`, `catatPembayaranLangsung`), as a third actor-facing exception beside Bayar and the webhook, because both write Billing's own tables (Tagihan, Bukti Pembayaran) and only the owning module may. Both settle through the existing `recordPayment`/`settleIn` path, so the downstream-effect registry (AC 5, ticket 25's Bukti Pemesanan included) fires exactly once, the same as a provider payment. A required proof file goes to the private FileStore first (like a Bukti Pencairan's transfer proof) and is deleted if the settlement is refused; its key is a new nullable `bukti_pembayaran.proof_key` column (null for a provider payment or the Rp 0 waiver). Both are audited in the *same* transaction as the settlement (new `AuditLog`/`FileStore` deps on `BillingDeps`, optional so every existing `billingOn` read-only caller is unaffected; a call without them throws `MissingBillingDep`, never silently no-ops).
  - **`reissueTagihan`'s due-date guard was generalised**, not special-cased to Harga Khusus: a pay-first Tagihan at or past its own due date now refuses any reissue with `tagihan_tidak_bisa_diganti`, whether or not the lapse tick has run yet (mirrors `notPayableBecause`'s own rule for Bayar). Covered directly in `tagihan.test.ts` and again through Harga Khusus in `harga-khusus.test.ts`.
  - **Harga Khusus** (`src/domain/billing/harga-khusus.ts`) carries every existing line across unchanged and adds the new negative line, so `reissueTagihan`'s own Rp 0 handling (`tagihan.ts`'s `issueIn`, from ticket 18) gives AC 4 for free — no extra code needed for the waiver. The reason is the Entri Audit's own `reason` field.
  - **The partner share** is recorded on the reissued Tagihan itself (`harga_khusus_porsi_mitra` + a required-when-nonzero `_catatan` column, both checked in Postgres). **Reading**: `reissueTagihan` only ever accepts a Tagihan that is *not yet paid*, and a Pencairan item is only ever created once a Tagihan *is* Lunas (and its burial recorded) — so in the ordinary case (a Harga Khusus set before the family pays) no item exists yet the moment the share is entered. For that case, `payouts/trigger.ts` (ticket 32) now reads the recorded share straight off the Tagihan when it later creates the Lokasi Mitra's items, and applies it there — oldest line first, an item it empties completely created already `dibatalkan` (`batalAlasan: "telah_ditanggung"`) rather than at Rp 0 — mirroring `kurangiPencairanPesanan`'s own rule. For the rare chance an item already exists (a second Harga Khusus on an order that already has one), the same transaction as the reissue also calls Payouts' `kurangiPencairanPesanan` directly — the integration point ticket 32 built and documented for this ticket (`payouts/item.ts`'s own docstring names it) — tolerating its "tidak_ditemukan" as the ordinary case above, not a refusal.
  - **Direct-payment reversal lives in Payouts** (`src/domain/payouts/pembayaran-langsung.ts`: `batalkanPembayaranLangsung`, Admin Platform only via the existing `pencairan.kelola`), because it undoes Payouts' own read of the payment (the platform-fee Potongan `trigger.ts` raised), never Billing's append-only record of it (the Tagihan, its Bukti Pembayaran and the "diterima oleh Lokasi Mitra X" method are untouched — AC 6 "immutability preserved"). Two states: before the tick has run, only a new `pencairan_pembayaran.dibayar_langsung_dibatalkan_pada` flag is set; after, the Potongan (new `dibatalkan` status, never a fourth deleted-or-rewritten state) is cancelled too. Either way the next tick (`trigger.ts`, now checking that flag) creates the Lokasi's ordinary tariff Pencairan items instead. A Potongan a Bukti Pencairan already netted, or one recorded paid offline, refuses reversal (`sudah_dipotong`): that money already moved.
  - **New Identity surface**: actions `tagihan.catat_pembayaran_manual` / `tagihan.tetapkan_harga_khusus` (Admin Platform, resource `tagihanResource()`) and `tagihan.catat_pembayaran_langsung` (that Tagihan's own Lokasi Mitra's Admin Lokasi, via `lokasiMitraResource`); the reversal reuses `pencairan.kelola`. New `AuditAction`s: `tagihan.catat_pembayaran_manual`, `tagihan.catat_pembayaran_langsung`, `tagihan.batalkan_pembayaran_langsung`, `tagihan.tetapkan_harga_khusus` (added to `src/lib/lokasi-labels.ts` too).
  - **No Server Action or page was built.** Every AC is met and tested at the domain layer (`billing.catatPembayaranManual` / `catatPembayaranLangsung` / `tetapkanHargaKhusus`, `payouts.batalkanPembayaranLangsung`), each already `guarded()`-ready (actor-checked, Zod-validated, audited); there is also no existing Admin Platform order-detail page to attach a manual-payment or Harga Khusus form to yet (`payouts` itself shipped the same way in ticket 32 — its own Admin Platform Pencairan-run screen is still unbuilt). Flagging rather than building a new page speculatively, since design and placement are the owner's call.
