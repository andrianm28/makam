# Chasing overdue pay-after Tagihan and Tidak Tertagih

Status: ready-for-agent
Blocked by: 25
Spec: Domain modules > 10. Billing (Chasing, Tidak Tertagih loss, blocks while overdue); 15. Notifications (reminder schedule); 14. Work Queues (Tier 3 Tagihan lewat jatuh tempo); stories 133, 160

## What to build

Chasing for pay-after Tagihan only (Saat Duka and burials under an existing Hak Pakai): automatic reminders at H+3/7/14/30 after the due date, an overdue list from H+1 with a call log, a Tier 3 Antrean row, Admin Lokasi push at H+1 and on Tidak Tertagih, and Admin Platform declaring Tidak Tertagih by hand from H+30 after at least one logged call. The Admin Lokasi gets a read-only list of its Lokasi's overdue Tagihan with the call log and can add notes. Expose the "overdue pay-after Tagihan on this Hak Pakai" query that blocks Perpanjangan and Ganti Pemegang Hak, and let the Admin Lokasi end the Hak Pakai once the Tagihan is Tidak Tertagih.

## Acceptance criteria

- [ ] Reminders to the Pemesan at H+3, H+7, H+14 and H+30 within 08:00–20:00, stopping as soon as the Tagihan is Lunas or Tidak Tertagih.
- [ ] The overdue list starts at H+1; call log entries carry outcome janji bayar / tidak diangkat / menolak / nomor salah; the row expects at least two calls, around H+1 and around H+14, made 08:00–20:00.
- [ ] The Admin Lokasi adds notes on the same call log for its own Lokasi's Tagihan and can't declare Tidak Tertagih.
- [ ] Tidak Tertagih is rejected before H+30 or with no logged call; after it the Tagihan stays payable.
- [ ] Admin Lokasi web push at H+1 and when the Tagihan is declared Tidak Tertagih.
- [ ] `isBlockedByOverdueTagihan(hakPakai)` returns true while a Lokasi Mitra Saat Duka Tagihan on it is Lewat Jatuh Tempo.
- [ ] Once Tidak Tertagih, the Admin Lokasi may end the Hak Pakai (Berakhir with reason); not for a burial under an existing Hak Pakai.
- [ ] Tidak Tertagih loss: no Pencairan is due for it unless the family pays later (enforced when ticket 32 lands; recorded here as the Tagihan state).
- [ ] Tests: reminder schedule and stop conditions; Tidak Tertagih guard (H+30 + a call); block query; end-Hak-Pakai permission after Tidak Tertagih only.

- 2026-09-28 — Builder readings, for the owner to confirm or correct:
  - **"The call log and its outcomes are unchanged" vs. AC2's four outcomes.** AC2 and spec.md both spell out `janji bayar / tidak diangkat / menolak / nomor salah`, which is a wider vocabulary than ticket 20's `sudah_dihubungi / tidak_diangkat / nomor_salah`. Read the 2026-09-26 comment as "reuse ticket 20's Telepon Pemesan *mechanism* (the table, `bukaTeleponPemesan`/`catatPanggilan`, the open/close lifecycle)", not "the outcome enum never grows" — the spec's outcome list otherwise has nowhere to live. Built: `teleponHasil` now adds `janji_bayar` and `menolak` alongside the three existing values (additive, no migration contract needed); `sudah_dihubungi` stays for the other call rows (a failed message, an order with no email) that were never given Chasing's richer vocabulary. Every "Telepon Pemesan" call form (Admin Platform's new page, and the existing Admin Lokasi one) now offers all five.
  - **"At least two calls" is not a hard gate.** AC2 says the overdue list "expects" calls around H+1 and H+14; only AC4's Tidak Tertagih guard is a hard rule ("at least one logged call"). Ticket 20's row closes on the first logged call, so "several calls over time" is modelled as several Telepon Pemesan rows opened and closed in sequence for the same subject (`bukaTeleponPemesan` reopens once the previous one is closed) — the H+1 escalation opens the first; nothing here auto-opens a second at H+14, since the spec gives that as guidance to staff, not a scheduled trigger. `teleponPemesanRiwayat` (new) reads the whole history so a call log page can show it.
  - **Where `declareTidakTertagih` lives.** Billing's own docblock says it is "called by the modules that own the orders … never by an actor directly", with Bayar and the webhook as the only two exceptions. Chasing has no owning order module (it is Billing's own spec subsection, and a further-burial Tagihan under an existing Hak Pakai has none), so `declareTidakTertagih(tagihanId)` is a plain, actor-free Billing function (matching every other Tagihan-status write there), and the new Server Action (`/staf/admin-platform/tagihan-lewat-jatuh-tempo`) calls it directly after `guarded()`'s own role check — the same shape `bayar` already has, just with a role check instead of a public-link one. Flagging this as a third, undocumented exception to that sentence rather than silently treating it as covered.
  - **No Entri Audit on `declareTidakTertagih`.** Billing has no `AuditLog` dependency today (unlike Pemesanan, Inventory, Notifications), and every other Billing status write (`recordPayment`, `batalkanTagihan`, the two lapse ticks) is unaudited too. Wiring one in for just this action would mean giving Billing a new cross-module dependency for one call; left as a follow-up rather than done here. `akhiriHakPakaiTidakTertagih` (Pemesanan's own, ending the Hak Pakai) **is** audited, since Pemesanan already has `audit`.
  - **The "H" in H+3/7/14/30 and H+1/H+30 is the Lewat Jatuh Tempo anchor** (`lewatJatuhTempoAt`, ticket 25 — the recorded burial plus its Lokasi's payment window), never the printed `dueAt` (the planned burial's). The two can differ when the actual burial happens later than planned; Chasing always counts from what actually happened, consistent with ticket 25's own rule for when Lewat Jatuh Tempo itself starts.
  - **Burial under an existing Hak Pakai** (spec stories 50–56, the "Makamkan di sini" flow) is not built yet — nothing in this repo issues a `pemakaman_hak_pakai_ada` Tagihan. Reminders, the overdue list and the block query are written generically over both pay-after moment kinds (so they need no change when that flow lands), but `isBlockedByOverdueTagihan` / `akhiriHakPakaiTidakTertagih` / the H+1 escalation's `lokasiId` lookup are scoped to the **Saat Duka grant order's own Tagihan** specifically (`pemesanan_makam.kind = 'saat_duka'`), which is exactly AC7's "not for a burial under an existing Hak Pakai" — and is automatically correct today since no other order kind exists to confuse it with.
  - **AC8 (Tidak Tertagih loss, no Pencairan)** needed no new code: nothing in Payouts triggers a Pencairan for a non-Lunas Tagihan today, so recording the `tidak_tertagih` status (this ticket) already leaves it with none; ticket 32 is where that gets asserted explicitly.
