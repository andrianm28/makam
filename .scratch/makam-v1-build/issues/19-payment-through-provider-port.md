# Payment through the PaymentProvider port and Bukti Pembayaran

Status: ready-for-agent
Blocked by: 18
Spec: Adapter ports > PaymentProvider; Domain modules > 10. Billing (Payment, Bukti Pembayaran); Testing Decisions > End-to-end 2; stories 35, 36 (Bukti Pembayaran)

## What to build

The pay page of a Tagihan, usable by anyone with the link (VA or QRIS): clicking Bayar asks the PaymentProvider to create a payment for the Tagihan, re-creating it if the provider's link expired; the platform's due date is independent of the link's. A route handler receives the webhook, verifies the Svix signature, parses it and processes it idempotently. A settled payment marks the Tagihan Lunas, issues exactly one Bukti Pembayaran and fires the downstream-effect hook that later tickets register on (Bukti Pemesanan, Pencairan due, Pekerjaan Layanan scheduled, Hak Pakai extended or created).

## Acceptance criteria

- [x] Bayar creates a provider payment on first click and reuses it while valid; after the link expires, Bayar creates a new one.
- [x] A lapsed (Dibatalkan) Tagihan can't be paid; a pay-after Tagihan that is Lewat Jatuh Tempo or Tidak Tertagih stays payable.
- [x] The webhook rejects a bad signature; the same event delivered twice yields one Lunas transition and one Bukti Pembayaran.
- [x] Bukti Pembayaran repeats the Tagihan's lines plus amount, method, time, reference and Nomor Tagihan.
- [x] A downstream-effect registry runs inside the same transaction as the Lunas transition (or enqueues jobs in it); a failing effect doesn't lose the payment.
- [x] Tests: Vitest with the fake provider (create, expiry re-create, signed webhook, duplicate webhook); Playwright E2E: a signed webhook payload posted to the running app marks a Tagihan Lunas and the Bukti Pembayaran page appears.

## Comments

- 2026-09-26 — Decided with the user after the Spec re-review: late payments are judged by the provider's `paidAt` against `dueAt` (spec, Billing), not by the lapse tick's timing; the same for manual payments.

**2026-09-26, build (agent):** built test-first on the Billing module's public interface (Vitest, real Postgres, FakeClock, FakePaymentProvider).

- **Bayar** (`billing.bayar(link)`): anyone holding a Tagihan's link. Under the Tagihan's row lock it reuses the newest provider payment whose link still has more than 5 minutes left, else asks the PaymentProvider for a new one (reference = Nomor Tagihan, amount = total, return URL = the Tagihan's public page on `APP_BASE_URL`), recorded in the new `provider_payment` table. The Tagihan's due date never moves. Refusals: `tidak_ditemukan`, `tagihan_dibatalkan` (lapsed or replaced), `sudah_lunas` (with the Bukti's link). UI: a "Bayar Rp …" button on the Tagihan page (print-hidden, existing `Button`, no new tokens), with a line explaining VA/QRIS and that Lunas shows once the payment arrives; a Lunas Tagihan shows "Lihat Bukti Pembayaran" instead. The page's `BillingDocument` now carries `payable` and `buktiLink`, so the page holds no status rule. Server Action `bayarTagihan` (`src/app/dokumen/[link]/actions.ts`) redirects to the provider's page (or to the Bukti once Lunas).
- **Webhook** (`POST /api/webhooks/pembayaran` → `billing.receivePaymentWebhook`): the route is thin (64 KB body cap → 413; Zod on the three `svix-*` headers; a refused signature → 401; everything Billing accepted → 200 so the provider stops redelivering; an error → 500 and it retries). The port's `parseWebhook` verifies the Svix signature and Zod-parses the payload. Billing records each event id in `payment_webhook_event` **in the same transaction** that acts on it (insert … on conflict do nothing), so a replay or a concurrent duplicate is `sudah_diproses` and a failed attempt is processed again on redelivery. A "paid" event for a payment made through Bayar settles the Tagihan: Lunas, one Bukti Pembayaran (method `penyedia_pembayaran` with the provider's channel, reference = provider payment id, time = when the provider says it was paid, never later than now), downstream effects. "expired"/"failed" change nothing (`diabaikan`; Bayar makes a new link). Money Billing cannot settle a Tagihan with changes nothing, answers 200 and is reported (Sentry, no personal data) as `perlu_ditinjau`: `pembayaran_tidak_dikenal`, `jumlah_tidak_cocok`, `tagihan_dibatalkan` (paid after the lapse), `sudah_lunas_dibayar_lagi` (a second payment on another link). Another event for the payment that already settled it is `sudah_lunas`.
- **Downstream effects**: `BillingDeps.paymentEffects: PaymentEffect[]` (`{ name, run(tx, SettledPayment) }`, exported from `@/domain/billing`). Every payment path goes through one internal `settleIn` → `issueBuktiPembayaranIn` (now in `settlement.ts`), which runs each effect inside the Lunas transaction in its own savepoint. A throwing effect rolls back only its own writes; the payment commits, the failure is recorded in `payment_effect_failure` and reported, and `billing.retryFailedPaymentEffects()` runs it again (idempotent; each effect must be idempotent too). **Seam for later tickets**: register Bukti Pemesanan / Perpanjangan, Pencairan due, Pekerjaan Layanan scheduled, Hak Pakai extended or created as effects where `createBilling` is composed (`src/server/runtime.ts`, the worker when it gets Billing); none is registered yet. **Not yet scheduled**: the retry needs the registry, and `SchedulerContext` is only `{ db }`; wire `retryFailedPaymentEffects` as a tick when the first effect is registered.
- **Judgement calls**: effects fire on every payment path, including manual `recordPayment` and a Rp 0 Tagihan at issue/reissue (spec: "every payment … fires the downstream effects"). Money received for a Dibatalkan Tagihan or twice for one Tagihan is reported, not refunded or re-opened (refunds are manual, Admin Platform). The `PaymentEvent` port gained `channel: string | null` (the fake sends "QRIS" unless told otherwise; ticket 61 maps SumoPod's); without one the Bukti reads "Pembayaran online (VA atau QRIS)". The Bayar action skips the guard like Masuk does (the link is the capability, anyone may pay); AGENTS.md lists only Masuk as that exception, so it may want a line for Bayar.
- **Lewat Jatuh Tempo / Tidak Tertagih**: nothing moves a Tagihan into them yet (chasing ticket), so the tests show a pay-after Tagihan past its due date is never lapsed and stays payable; both statuses are in the one `PAYABLE` list Bayar, `recordPayment` and the webhook share.
- **E2E**: `e2e/pembayaran.spec.ts` seeds the e2e Admin Platform and an example Tagihan with a new development/test-only CLI, `node dist/seed-tagihan.mjs` (refused on staging and production; on a stack with no Pengaturan Operator it first enters example values as the stack's first Admin Platform), clicks Bayar, stands in for the fake provider's page, posts a Svix-signed "paid" webhook to the running app, and checks Lunas and the Bukti Pembayaran page (4.5 s). Override the seed with `E2E_SEED_TAGIHAN`, like `E2E_SEED_ADMIN`.
