# Image retention and disk hygiene on the shared host

Status: ready-for-agent
Blocked by: 72
Spec: Implementation Decisions > Architecture; ADR 0002 (second amendment of 2026-09-26)

## What to build

Decided with the user on 2026-09-26, after the shared host's disk filled up. Keep makam's footprint on the host bounded without touching other projects.

## Comments

- 2026-09-27 — Orchestrator: third pass reviewed and the re-reviewer — who had found the two holes — now states the script **is fail-closed**, and proved it rather than asserting it: breaking `pipefail` turns the guard red, removing `defaults:` turns it red, running the CLI on truncated deployments gives exit 78 with nothing deleted, and every odd image-id shape tried (bare `sha256:`, UPPER, 11/13/63 hex, a word, multi-line) is refused with zero removals. `rm` only ever reaches `…:sha-…1` and `…:sha-…3`; `latest`, `v*`, FFI's images and postgres are unreachable. 29 versions and `latest` are still on the host — nothing real was ever deleted.
  - **Two gaps left, both harmless to data, and recorded so they are not forgotten.** (1) The ratchet skips documentation and lock files (`.md`, `.txt`, `.lock`, `.log`), so a `docker image prune` written in `docs/ops/runbook.md` or in a comment position passes CI. Nothing executes from those files, so no image can be removed through it — it is completeness, not safety. (2) A `null` deployments response (as opposed to a truncated one) gives exit 0 and green, but names zero versions, so nothing is deleted. Worth tightening when this is next touched; neither can destroy anything today.
  - **Merged to main** after three review rounds. The owner then runs, as two deliberate steps: `deploy/install-host.sh` once, then `makam-prune-images --env staging` (with `--dry-run` first). The script refuses with exit 78 and zero deletions when the daemon is unreachable, when the inventory cannot be read, when the env file names a different image, or when `deployed.env` does not name the running version. **Until those two steps are run, the 14.7 GB stays** — that was the builder's decision, and it was the right one: at the time it built this, the in-use protection was inert.

## Acceptance criteria

- 2026-09-27 — Orchestrator: Standards axis on `5355e1b`. **Verdict: not fail-closed. Do not merge, and do not run the script, until 1 and 3 are fixed.** These are the two axes merged here; both must be fixed in one pass.
  - **HARD 1 — the "image in use is never removed" protection is inert, and that is the whole safety of this script.** `deploy/bin/makam-prune-images:126-128` compares a string built from `docker inspect {{.Image}}`, which is `sha256:<64 hex>`, against `$id` from `docker image ls {{.ID}}`, which is the **12-character short form**. The two can never be equal. The reviewer demonstrated it on this real host: feeding `"aaaa…"` and `"sha256:aaaa…"` produced `OFFERED TO DOCKER`. So a running container's image **would be offered to Docker for deletion** — while the script's own header says "an image in use is never even offered to docker" and the runbook says "**kept, always**". The test does not catch it because `tests/tooling/makam-prune-images.test.ts:20` builds its fake with a full `sha256:` id on **both** sides, so it proves the fake's configuration rather than the behaviour. Normalise the ids on both sides (full digest, or short-to-full via `docker image inspect`) and add a test that deliberately feeds a short id on one side and the full digest on the other.
  - **HARD 2 — the ratchet that guards against global prunes is blind where it matters.** `tests/tooling/image-retention.test.ts:18` only matches `.ts|mts|mjs|sh|yml|yaml`, so the **11 extension-less executables in `deploy/bin/`** — including `makam-prune-images`, `makam-deploy` and `makam-diskcheck` — are never scanned. `docs/`, `e2e/`, `.claude/hooks/`, `src/` and `docker-compose.yml` are not scanned either. The claims in AGENTS.md and the runbook that it "fails the build if one appears" are false: `docker image prune -a` written inside `makam-prune-images` would pass CI. Widen the scan to every tracked file, or narrow the claim to exactly what is scanned — and make the scan part of the repo's own checks so it cannot rot. It also only strips `#` comments, so a `// docker image prune` in a TS comment trips it; handle both comment styles.
  - **HARD 3 — the ghcr side fails *open*, the opposite of the host side.** `scripts/images/expired-versions.ts:73-82`: an empty or malformed Deployments API response becomes `keep = []` ("none recorded") and then deletion proceeds on age alone. The reviewer confirmed both old versions would still be named for deletion. `.github/workflows/image-retention.yml` also requests `per_page=100` without `--paginate`, and GitHub purges deployments, so an empty list is the normal state after a while. That directly contradicts the runbook, and it is the opposite policy to `makam-prune-images`, which refuses when `deployed.env` does not name the running version. **Fail closed on an unreadable or empty list** — if you cannot prove a version is not deployed, keep it. Paginate the API too.
  - **HARD 4 — do not credit the `deployed-release.ts` fix to this ticket's CI.** `:79-86` is correct and minimal, but `ci.yml:140`'s `|| true` means the `migrations` job has always fallen through to `RUNNING: …:latest`. This fix activates a code path that has never actually executed, and nothing in this diff proves the job is green. Verify it on `main`'s CI, and give the top-level-`await` fix its own ticket with its own test.
  - Judgement calls: `makam-prune-images:103` discards a malformed `PREVIOUS_TAG` silently, asymmetric with `running` at `:101` (verified benign because `deploy.log:264` keeps `KEEP>=2`, but the smell is real — fail or report, don't shrug); `:132-133` logs an `image rm` failure and still exits 0, so "exit 0" stops meaning "retention was enforced" — separate the exit codes; and there is still no `--dry-run` on the host script, which the Spec axis also flagged.
  - **Verified good, and worth the record:** scope is tight (`IMAGE` must equal the allow-list before any `rm`, so `v*`, `latest` and other repositories are unreachable); ordering is right (inside the healthy branch, any exit); `deployed.env`, the daemon and an unreadable inventory all refuse with exit 78 and zero deletions; and the cross-environment race is handled at `deploy.log:264`. The two gaps above are what stop this being fail-closed.



- 2026-09-27 — Orchestrator: Spec axis on this branch. **Nothing in this ticket's file had been touched**, which is itself a finding, and one that matters most here: the builder deliberately deleted **no real image** and called the 14,7 GB an owner decision — but that decision existed only in a report to the orchestrator. Merging it that way leaves the host at 91 % with the new alarm ringing and nothing in the repo saying what was decided or by whom. Recorded here now; it stays the owner's call.
  - **The runbook tells you to look, not what to do.** "What to do when it warns: `makam-prune-images` first … then `docker image ls | head -50` … never a prune." AC 4 is literally satisfied, but there is no action for the case that actually happens on this host — the disk pressure is mostly **other projects' images**, which this ticket must never touch — and nothing escalates to the owner. Say what to do when the space is not ours, and who to tell.
  - **There is no `--dry-run` for the host prune.** The ghcr side has `dry_run`; `makam-prune-images` does not. Worse, the runbook's code block runs the **destructive** command first and shows `docker image ls` as the "preview" *afterwards*. For a first run on a shared host that ordering is backwards. Add a dry run that lists exactly what it would remove and deletes nothing, and make the runbook show it before the real thing.
  - **"in this repository" is overstated.** AGENTS.md and the runbook both claim `tests/tooling/image-retention.test.ts` fails the build if a prune without a name appears anywhere in the repository. It scans `deploy`, `scripts` and `.github` (ts/mts/mjs/sh/yml) only — not `package.json`, `docker-compose.yml`, `e2e/`, or the docs. Either widen the scan or narrow the claim. (It also only strips `#` comments, so a `// docker image prune` inside a TS comment is a false positive — cheap to fix while widening.)
  - **One sentence is missing about why "3 versions per env" is safe.** It holds only because `rollback.yml` re-resolves a digest from ghcr rather than a local tag. State that dependency explicitly, or a future change to the rollback path silently breaks the guarantee the retention set is built on.
  - **Out of ticket, and it needs its own ticket:** the fix to the top-level `await` in `scripts/migrations/deployed-release.ts`. It is correct and necessary here (the retention CLI imports that module), but it changes what the migration-upgrade test in `ci.yml` actually exercises — the test had been silently falling back to `ghcr :latest` and now reads a real successful deployment. That deserves a ticket of its own with a test, not a mention here.
  - Verified good: the tests assert real outcomes against a fake inventory and check *which* images were asked to be removed; `deployedDigest` reuse is sensible; the `makam-deploy` change is **required**, not scope creep — AC 1 replaces its 5-tag retention, and the call site is unchanged.

## Acceptance criteria

- [ ] Every deploy (the host's `makam-deploy`) keeps at most the last 3 makam image versions per environment on the host (the running one and the previous one always among them) and removes only `ghcr.io/andrianm28/makam` images; other projects' images are never touched.
- [ ] A monthly GitHub Actions workflow deletes ghcr `sha-*` versions older than 30 days, except any currently deployed to staging or production and any `v*` release tag.
- [ ] Dev work: AGENTS.md tells builder agents to remove their own compose stack, dev image and `node_modules` when a ticket is merged, and names the per-worktree image tag pattern so the cleanup is exact.
- [ ] A disk check (on the existing health timer or GlitchTip/uptime alarm) warns when the root disk passes 85%.
