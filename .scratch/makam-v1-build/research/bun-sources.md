## 1. Next.js on Bun
- Local Next docs (node_modules/next/dist/docs): Bun appears only as a package-manager tab (`bun dev`, `bun add`, `bun create next-app`) in e.g. 01-app/02-guides/scripts.md and package-bundling.md. No page lists Bun as a supported runtime; installation.md states "Minimum Node.js version: 20.9" (01-app/01-getting-started/01-installation.md). Conclusion: Next's own docs treat Bun as package manager only.
- Bun docs: https://bun.com/docs/guides/ecosystem/nextjs says prefix Next CLI scripts with `bun --bun` (dev/build/start) so Bun, not Node, runs the Next CLI; SSR, static generation and API routes "work with Bun".
- Bun 1.4 blog https://bun.com/blog/bun-v1.4.md: "`bun --bun next build` works on Next.js 16.3 with Turbopack and the React Compiler".
- Caveat evidence: https://community.vercel.com/t/next-js-16-3-bun-runtime-1-3-12-build-failure-on-vercel-while-bun-1-3-14-works-locally/47139 : Next 16.3 under Bun 1.3.12 fails with "Failed to load external module next/dist/compiled/next-server/app-page-turbo.runtime.prod.js: TypeError: Expected CommonJS module to have a function wrapper"; works on 1.3.14; the thread's workaround is Bun as package manager only, plain `next build`. Shows Next-on-Bun-runtime breaks across Bun patch versions.
- Which Next runtime features work under Bun (middleware/proxy, after(), ISR cache, image optimisation with sharp, standalone server.js): UNVERIFIED, no primary page found.

## 2. Vitest vs `bun test`
- Vitest docs https://vitest.dev/guide/ : requires "Vite >=v6.4.0 and Node >=v22.12.0"; "If you are using Bun as your package manager, make sure to use `bun run test` instead of `bun test`, otherwise Bun will run its own test runner." No statement on running vitest on the Bun runtime.
- Bun 1.4 blog (above): "vitest runs under Bun, including `--coverage`, with the threads and forks pools." So `bun --bun vitest` is now claimed to work. Earlier history: https://github.com/oven-sh/bun/issues/4145 (worker_threads options argv/execArgv/resourceLimits unimplemented, 2023); https://github.com/vitest-dev/vitest/issues/8232 (Bun 1.2.17 + Vitest 3.2.4: `-b` flag gives "ReferenceError: Cannot access 'dispose' before initialization" in tinypool worker init; works on Node; closed). Whether Vitest 5.0.2 specifically is clean on current Bun: UNVERIFIED (not run).
- `bun test` (Bun's own runner, Jest-style): https://bun.com/docs/test/runtime-behavior : runs all tests "in a single process by default" (shared global state; faster startup); `vi.fn` etc exposed globally. https://bun.com/docs/test/mocks : `vi.mock`/`jest.mock` via `mock.module()`; "Bun does not support the `__mocks__` directory or auto-mocking"; vi helpers listed: fn, spyOn, mock, restoreAllMocks, resetAllMocks, clearAllMocks (vi.stubEnv, vi.hoisted, vi.importActual, vi.waitFor not listed there: UNVERIFIED). https://bun.com/docs/test/dates-times : `setSystemTime`, `useFakeTimers/useRealTimers` supported, but "In bun:test, Date constructor does not change when you useFakeTimers" (differs from Vitest/Jest fake timers). Bun 1.4 adds `--isolate`, `--parallel`, `--changed`.
- No `globalSetup`/`provide()`/`inject` equivalent found in Bun docs: bun test has `--preload` instead (UNVERIFIED; not fetched). makam's tests use `globalSetup` + `ProvidedContext.databaseUrl`, so `bun test` means rewriting setup and 42 mock/timer files; staying on Vitest-under-Bun avoids that if the claim in 1.4 holds.
- Test-speed reasoning (no primary benchmark found, UNVERIFIED as a number): suite is Postgres-bound (real DB, DB reset between cases, `fileParallelism:false`, container start in globalSetup). Bun's gains (startup, transpile) affect only per-file overhead, which `fileParallelism:false` and DB I/O dominate. Measure `npx vitest run` vs `bun --bun vitest run` before deciding.

## 3. Libraries
- pg: README of pg-boss says runtime "Node 22.12 or higher, or Bun" (https://github.com/timgit/pg-boss) => Bun is a stated target of pg-boss 12. node-postgres on Bun: no official compat statement fetched (UNVERIFIED); search result cited oven-sh/bun#17173 (prepared statement already exists, closed), but that concerns Bun's own `sql` tag, not `pg`.
- Bun.sql: https://bun.com/docs/runtime/sql : native Postgres client, pooling, transactions, savepoints, LISTEN/NOTIFY; unimplemented: column-name transforms, COPY, PostGIS/GSSAPI; large ints returned as strings unless `bigint:true`. Drizzle: https://orm.drizzle.team/docs/connect-bun-sql : `drizzle-orm/bun-sql`, but the page's install line is `drizzle-orm@rc` / `drizzle-kit@rc`, i.e. pre-release on the page fetched; makam is on 0.45.x with `pg`. Switching would also change pg-boss (uses its own db layer; can accept custom executor, UNVERIFIED) and `inTransaction` code. Not needed: `pg` is claimed to run on Bun.
- Node API gaps relevant here, from https://bun.com/docs/runtime/nodejs-compat : child_process partial (IPC no HTTP sockets), async_hooks partial ("Bun does not invoke hooks, apart from `init` for `process.nextTick`; async ids always 0"; AsyncLocalStorage implemented), diagnostics_channel partial (missing http.server.*, net, module, child_process, worker_threads channels), worker_threads partial (resourceLimits ignored in that page), tls partial, net/vm/http2 green. Search snippet (bun.sh nodejs-apis page, UNVERIFIED version) listed node:crypto as missing ECDH among others: relevant to `web-push` (VAPID/ECDH) and not confirmed current.
- Sentry: https://docs.sentry.io/platforms/javascript/guides/bun/ covers `@sentry/bun`; "Bun has no runtime hook Sentry can use to instrument those packages", needs `sentryBunPlugin` at build for dependency spans. It does not address `@sentry/nextjs` under Bun (UNVERIFIED). `@sentry/node` (used by src/worker/sentry.ts) on Bun: UNVERIFIED; OpenTelemetry-based instrumentation hooks (diagnostics_channel/require hooks) are the likely gap, consistent with the page above.
- Playwright: https://playwright.dev/docs/intro lists Node "latest 22.x, 24.x or 26.x"; no Bun mention. Bun 1.4 blog: "Playwright now runs on Bun: drive a browser with `connectOverCDP()`, run your suite with `playwright test`." Older https://github.com/oven-sh/bun/issues/2492 (Bun 0.5.8 failure, closed). Official Playwright support for Bun: none stated. Keep Playwright on Node regardless (browsers are separate processes anyway).
- nodemailer, web-push, svix: no Bun-specific primary source found: UNVERIFIED.
- better-auth: docs mention Bun via Hono quickstart (`bun x create-hono`), https://better-auth.com/docs/integrations/hono; no explicit runtime support matrix for Next-under-Bun (UNVERIFIED). better-auth here uses Next + pg/drizzle.
- Testcontainers (@testcontainers/postgresql, used by tests/global-setup.ts) on Bun: UNVERIFIED (uses Docker socket, dockerode, node:http / streams).

## 4. Docker / deploy
- Bun's guide https://bun.com/docs/guides/ecosystem/docker : base `oven/bun:1`, multi-stage, `--frozen-lockfile`, `USER bun`. Makam pins the Node image by digest and the policy requires digest pins; an `oven/bun` digest would need to be chosen and Dependabot docker updates apply the same way (UNVERIFIED for oven/bun).
- Next standalone output (`.next/standalone/server.js`): running it with `bun server.js` is UNVERIFIED in official docs. Alternative low-risk path: keep node:22 for runtime, use Bun only for install/dev tooling.
- The worker/migrate bundles are esbuild `platform:node` .mjs; running with `bun dist/worker.mjs` is possible in principle (UNVERIFIED), but pg-boss 12 advertises Bun support.
- Chromium (apt) in runner stage is runtime-agnostic: `execFile` of chromium-headless-shell in src/adapters/live/chromium-pdf-renderer.ts uses child_process (partial in Bun, plain execFile not documented as a gap).
- Sentry source-map upload (scripts/collect-sourcemaps.mjs, CI `sourcemaps` job) is runtime-independent but `withSentryConfig` plugin under `bun --bun next build`: UNVERIFIED.

## 5. Production risk (summary, from evidence above)
1. Next 16.3 on Bun runtime has a documented breakage on Bun 1.3.12 (Vercel thread), fixed per that thread by 1.3.14, and Next's docs list only Node >= 20.9 as the runtime. Version pinning would be mandatory; support is the Bun team's, not Vercel's.
2. Observability: Sentry's Bun guide admits no runtime hook for dependency instrumentation; @sentry/nextjs under Bun is not documented. Privacy scrubbing (src/lib/observability/scrub.ts) behaviour under Bun: UNVERIFIED.
3. Money paths (Billing/Payouts/Refunds) depend on pg transactions and pg-boss locking; pg-boss states Bun support, pg on Bun UNVERIFIED. A test-vs-prod runtime split (tests on Bun, prod on Node) would reduce the evidence value of tests; a full move needs the whole suite plus e2e on Bun.
4. Process/CI churn: lockfile, `npm run deps` hard-link store, `npm audit` gate, Trivy, image digests, and `node dist/migrate.mjs` in ci.yml all assume Node/npm.
5. Cheapest experiments (not run): `bun --bun vitest run` on a few files and compare time to `npx vitest run`; `bun install` as package manager only (Vercel thread's own recommended fallback).
